## Update, 2026-10-10 — the completeness sweep, and the low-precision inversion

The question was "is that *all* of it?". It was not. Sweeping every target of
every crate in the root workspace (CPU cell and cuda cell) found five more of
OUR gates dead on 0.22 — and, in the same sweep, two machine facts that the
port made false.

### What the sweep found and fixed (all ours)

| id | defect | why it was red | fix |
|---|---|---|---|
| B4 | **The root workspace's own tests did not compile**: `TensorData::bytes` is a method on 0.22 (2 sites in `model_seam.rs`, 1 in `msa_gate1_flex.rs`) — the same class as B1, one workspace over | a gate that cannot compile reports nothing | `.bytes()` |
| B5 | **`gr_seam` 3/3 red** — its fixture inherited `DormouseConfig::default()`, which is deliberately the *byteflow A/B winner net* (`schema.rs:809`, `use_byteflow = true`), while `mor_bce_weight` defaults to 0.05, so `validate` refused loudly. The fixture never changed when the default flipped | fixture older than the default it inherits | `use_byteflow: false` in the fixture (it tests GR, not byteflow) |
| B6 | **`bf16_compute_on_cpu_is_the_fp32_answer_and_says_so` red under `--features cuda`** — the "drop on non-CUDA" arm was guarded by `#[cfg(feature = "cuda")]`, i.e. the BUILD, not the DEVICE, so a cuda build on the Flex device took the bf16 arm and moved 1.898 | compile-time guard where the contract is a runtime device property | device check (`matches!(x.device().as_dispatch(), DispatchDevice::Cube(_))`), the drop is now computed, not compiled in |
| B7 | **`preset_exec` 2 tests red** — `plain9m` shipped with no COVERED/cost-list entry; the depth override assumed every preset reaches depth 2 (the depth-1 control cannot, and the setter refuses loudly); the Muon+ formula `4*n_experts + 3` assumed TSCT | the preset landed; the gate did not follow | three test-side generalizations, and the formula now reads `use_tsct ? 4*n_experts + 2 : 0` plus the engram key projection (which is Muon-routed in BOTH topologies) |

And the honest negative that closes one of them: `bf16_matmul_on_flex_is_the_fp32_answer`
(pinned in `param.rs`) proves the **raw** bf16 op is honest on Flex *bare and
through the autodiff bridge*. So B6 is entirely ours — the guard was hiding a
path, not causing a wrong kernel.

### The low-precision inversion (0.22, measured 2026-10-10, one dtype per process, release)

| shape | fp32 | f16 | bf16 |
|---|---|---|---|
| 5120x768x2048 | 0.94 ms / **17.19** | 2.06 ms / 7.83 | 0.44 ms / **36.84** |
| 5120x2048x8192 | 8.58 ms / **20.03** | 20.14 ms / 8.53 | 3.90 ms / **44.06** |

- **ADR-0016 bug 2 is dead on 0.22.** Both bf16 parity tests in `backend-parity`
  (`bf16_matmul_cuda`, `bf16_gemm_cuda`), `#[ignore]`d by that ADR, now PASS, and
  bf16 matmul runs at 44.06 TFLOP/s — the cuBLAS ceiling, 5.2x 0.22's own fp32.
  A new gate arm (`bf16_gemm_speed`, `bf16_gemm_speed_model_shape`) carries the rate.
- **The f16 tensor-core path is NOT alive on 0.22**: 7.83-8.53 TFLOP/s, 4.7x below
  the 39.75 TFLOP/s the cubecl-ir patch bought on pre.4 and 2.4x below 0.22's own
  fp32 — and STABLE across 4 runs (8.47-8.50), so it is **not** A1's coin flip
  choosing a slow candidate; it is the route.
- **The cause of the f16 regression is ours**: `ae80b53` cut every
  `[patch.crates-io]` for the port on the stated premise "stock 0.11.0 covers
  f16 sizing". That premise is now measured false. The asymmetry (bf16 fast, f16
  slow, one stack, one harness) is a cubecl 0.11 question worth the upstream
  issue — and re-landing the cubecl-ir patch is our own candidate experiment.
