# bf-compat — ByteFlow patch tokens × the dormouse loop (compat channel)

Lane: **bfcompat**. Worktree `wt/bfcompat`, branch `wt/bfcompat`. CPU-only
(flex/CPU backends — the GPU was running another job, and none of these gates
needs it), NaN firewall untouched, no merge to main, no 1M work.

Status: **LANDED** — this file is committed with the gates it names; the hash
is the commit that carries it.

## 1. The seam

Failure map: `docs/reviews/byteflow-ab-2026-10-02.md`. Gate sites:

- `crates/dormouse-core/src/config/validation.rs:308-400` — the `use_byteflow`
  refusal block (7 arms, 4 aux weights, `moe_topk`, the window/shape Errs).
- `crates/dormouse-train/src/byteflow.rs:82-127` — `check()`, the train-side
  flags (`--bf16`, `--graph-capture`, `--jepa-targets`, `--engram-ram`,
  `--rand-depth`, `--eval-depths`, `--stress`, `--opt ∉ {adamw, mix}`),
  applied to BOTH byteflow dispatch modes.

The lane's one change to that picture: `use_byteflow` + `use_kda` is no longer
a refusal. It runs the **compat channel**:

```text
bytes [b,t] → ByteFlow front stage (embed + local encoder + coding-rate
    Top-K chunker + proj d_local→d_global)  →  patch latents z [b,K,d_global]
            → in_proj [d_global → d_model] → dormouse LoopBlock (KDA over K
    patch positions, `targets = None`) → out_proj [d_model → d_global]
            → ByteFlow decode_chunks (upsample + decoder blocks + byte head)
    → logits [b,t,256]
```

`BfChannel` (`crates/dormouse-core/src/bf.rs`) owns the two pairing `Linear`s
plus ByteFlow's own params, with `g_layers = 0` so `net.global` builds empty —
the byteflow-side checkpoint record stays byte-identical to the standalone
arm's, and `ByteFlowNet::forward` (never called here) would refuse K=0 loudly.

### The objective: the DECODER'S byte CE

`forward_channel` (`crates/dormouse-core/src/model.rs:450`) runs the loop with
`targets = None` and returns `rec` = mean CE of the decoder's `[b,t,256]`
logits against all T labels; `aux = None`. Two reasons, both load-bearing:

1. `decode_chunks` is the model's only exit. A loss taken at K patch starts
   would leave `upsample_w`, `decoder` and `out` with no gradient — a dead back
   stage behind a healthy loss curve (the `8fa5d4c` shape).
2. The held-out eval scores `[b,t,256]` logits against all T bytes, so the
   train objective and the eval line are the same quantity. A K-position CE
   would not be.

The earlier draft of this document described a K-position CE through the
loop's `L_Rec`. That contract was **rejected** during implementation for
reason 1; the byte CE above is what shipped.

## 3. Dispatch and the arm line

`train/src/lib.rs:958-990`: `byteflow::check(&cfg)?` runs first for BOTH
modes, then `if !bf::compat_armed(&dorm_cfg) { return byteflow::train_loop(..) }`
— the standalone arm is unchanged; `bf::compat_armed` (`bf.rs:90`) is the ONE
list, and `validate` refuses the same arms by name, so a config reaching the
dispatch has already been ruled on. The duplicate `compat_channel_armed` in
train was deleted.

The step-0 line (COUNTED, `lib.rs:985`):

```text
byteflow compat arm: front/back stages + dormouse loop (byteflow_g_layers replaced by the loop) over k={} patches of t={} bytes (patcher={}, opt={}) aux=none host-tables=none
```

`opt=` is `build_optim`'s router, i.e. the same one as the dormouse path: the
stages' 2-D `Linear`s are Muon+ ColRow under `--opt mix`, not AdamW. An earlier
draft of this line ended `byteflow-stages=AdamW(rest)`; that was false for the
channel and would have been an ADR-0011 mark naming the wrong thing.

The eval line carries `bf={runs}` — the channel's own forwards during the
eval. `bf=0` there means the eval scored a different network than the one
being trained (the §3.2 defect shape).

## 5. Fixture note (a capacity shrink, not an arm switch)

`preset_exec::fixture` shrinks `byteflow_k_tokens` to **8** when
`c.use_byteflow`, because the byteflow presets ship K=128 over SEQ=32 fixtures
and `K ≤ T` is asserted in `encode_chunks`. This is a **capacity** field (the
`max_seq_len` class), which is why it is deliberately NOT in
`execution_fields` — that list is arm switches, and adding capacity there
would let a preset silently run at a different width than it ships. K=8 is
less than the attention arm's chunk size of 16 (`attention.rs:120`), so
`byteflow_kda_executes` proves the partial-chunk path too; the trainer's own
gate uses K=16 = exactly one full chunk.

## 6. Findings outside the lane

Two were **pre-existing at HEAD and are fixed here** (both proven pre-existing
by running the same test at HEAD, message and all):

1. **`configs/p150.toml` shipped without `use_byteflow = false`** — it made
   `preset_exec::p150_executes` and `…::a_preset_that_declares_an_arm_it_never_enters_fails_here`
   red. The schema default flipped to the winning byteflow net on 2026-10-02
   with the rule "every dormouse preset lists `use_byteflow = false`
   explicitly"; p150 was the only one of thirteen that did not, so
   `preset(p150)` panicked inside `validate`. One line + a comment.
2. **`aux.rs::mini()` (the DSpark regression config) had no `use_byteflow`**
   either, so with `use_engram` defaulting on it armed the channel and
   `forward_channel`'s aux `assert!` fired — `aux::tests::dspark_aux_does_not_read_the_label_sequence`
   is the test §3.3 calls the DSpark fix's gate, and it went red the moment the
   channel existed. One line, the same one-liner `loop_block.rs:1282,1500`
   already carry. This one is *caused* by this lane (before it, `use_byteflow`
   was unread inside `core`), which is why it is fixed and not filed.

Three are **reported, not fixed**:

3. **`--seq-len < byteflow_k_tokens` panics inside `encode_chunks` naming no
   flag.** Nothing ties `TrainCfg.seq_len` to `byteflow_k_tokens`; `validate`
   compares the CONFIG's `max_seq_len` but the trainer's `--seq-len` is a
   separate field. The standalone arm bites identically — pre-existing, not
   introduced here. Cheapest fix: one Err in `byteflow::check` (and/or
   `resolve`) naming both fields.
4. **`--set use_msa=true` is not a config key** (`config/override.rs:164-172`
   lists every other `use_*` arm). The field exists in the schema and
   `validate` refuses it with `use_byteflow`, so the only way to turn MSA on
   from the CLI is a preset file. Pre-existing; the refusal gate asserts this
   one at `validate` directly instead of through `resolve`.
5. **`DormouseConfig::default()` does not pass `validate`.** The default is
   the schema default — `use_byteflow = true` (`schema.rs:111`) *and*
   `use_kda = true` (`:308`) *and* `use_engram = true` (`:331`) — which the
   block this lane edited refuses. So "a flat preset missing the field gets
   the winning net" (`schema.rs:654`) is only true of a net that also has to
   switch its arms off; `configs/byteflow.toml` does exactly that
   (`use_kda = false`, `use_engram = false`), but nothing says so at the
   default. Pre-existing since the 2026-10-02 flip, LOUD (resolve names every
   offending arm), so it is a schema-doc gap rather than a defect class — and
   it is the reason `aux::mini()` above armed a channel at all. Changing a
   default is an owner decision; not taken here.
6. Aux heads on the channel (width-aware `out_acc`), then re-look at the aux
   refusals; and Engram/MoR/GR/AttnRes on the channel. Same method, none
   attempted.
