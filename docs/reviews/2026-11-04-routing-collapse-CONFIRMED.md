# 2026-11-04 — ПОДТВЕРЖДЕНО: 432 из 512 экспертов мертвы

## Замер

`scripts/route_hist.py` на чекпоинте `m400` (шаг 149 999), **реальные байты**
из `fwedu.bin`, b4 × s1024, 8 192 назначения:

```
живых экспертов:      80 / 512   (15.6%)
максимум на эксперта: 678        (8.3% всех токенов)
top-10 держат:        50.1% всех токенов
среднее:              16.0
```

На случайных байтах тот же чекпоинт даёт 439/512 живых — то есть **коллапс виден
только на реальных данных**, и именно поэтому он не всплывал раньше.

## Что это значит

1. **Половина параметров модели (банк 100M из 199M) не работает.** «512 экспертов»
   — это фактически 80, из которых половина трафика идёт в десять.
2. Объясняет замер `E=512 хуже E=256 на 0.033`: больше мёртвого веса при том же
   числе работающих экспертов.
3. Объясняет, почему 199M не отрывается от 105M так, как должна.
4. **Dropless-режим это скрывал**: нет счётчика дропов — нет сигнала.

## Почему LFB не вытянул

`experts.py:1024`: `lfb_bias.sub_(coef * sign(L_e - mean(L)))` — **знаковый**
интегратор с шагом `coef=0.01` по **кумулятивным** счётчикам.

- мёртвый эксперт (L=0) получает `+0.01` за шаг: чтобы догнать живого, нужно
  ~сотни шагов, а его собственные веса за это время не учатся (нет градиента)
  → классический rich-get-richer, из которого знаковый контроллер выбирается
  слишком медленно;
- при каждом resume `lfb_counts` и `lfb_bias` начинаются заново (мы возобновляли
  прогон 5+ раз), то есть контроллер ни разу не отработал длинно.

## Следующие шаги (в работе)

1. Заменить знаковый шаг на **пропорциональный** (`b -= γ·(L_e − mean)/mean`),
   с гейтом: на 2 000 шагах доля живых ≥ 80%, распределение не осциллирует.
2. Или **aux load-balancing loss** (Switch/GShard) как второй арм для A/B.
3. Перезапуск прогона с исправленным роутингом — владелец разрешил начать заново.
4. `batched`-ядро (8.6×) включается только после того, как банк распределён:
   сейчас банк `[E, max_group, d]` требует 12 ГиБ из-за одного эксперта с 4 096 строк.
