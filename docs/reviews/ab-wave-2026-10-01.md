### 0.2 The seeds are 1/2/3, and "1001/1002/1003" is a filename

`first_run.sh`'s log pattern is `first_run_${STEPS}_$(date +%m%d_%H%M).log`.
`first_run_2000_1001_0037.log` is **Oct 01, 00:37** — `1001` is the *date* and
`0037` the time, not a seed. The seeds on record are 1, 2, 3 (from the ckpt
names `--seed-2-`, `--seed-3-` and the `seed = 1` in the config snapshot).

So the wave runs **seeds 1/2/3**, paired against the control's seeds 1/2/3. This
is deliberate and it is the better design: `--seed` is a pure function of model
init and the JEPA mask (§3.7), so a same-seed pair starts from the same
initialisation to within the measured TSCT residue (≤1.04e-06 relative), which
removes the init term from the comparison instead of adding a second variance
source. Running seeds 1001/1002/1003 would have compared against a control
measured on 1/2/3 and charged the difference to the arm.

`rope-2026-09-30.md:275-277` says so in its own words: *"**Not wired to the

### 2.2 MoE — top-1 of 3, and why not 4

The arm's own fixture and its headline number are 4 experts / top-1
(`moe-routing-2026-10-01.md:1`, "dense shared FFN vs 4× top-1 at equal ACTIVE
FFN FLOPs"), and `small` ships **`n_experts = 3`**. Raising `n_experts` to 4 to

param-neutral routing A/B into a capacity A/B, so the wave runs the shipped
`n_experts = 3` with `--set moe_topk=1`: **top-1 of 3**, still param-neutral
(`num_params` equal at `moe_topk` 0 and 1 is the crate's own gate), which is the
property that makes it comparable to the control at all. `moe_lb_coef` stays
**0.0** — the report ships no coefficient ("no coefficient is shipped, and
`moe_lb_coef` stays 0.0 with the arm off"), and `lb > 0` with routing off is
refused.

**Stated limit on this arm's evidence:** routing is the one arm here whose
on-position does not change `params=`, and `probe::MOE_ROUTE` is **not on the
log line** (only `fb=` and the legacy seams are). So for MoE, "the arm ran" is
carried by the resolved-config snapshot plus the crate's own
`off_is_the_dense_blend_bit_for_bit` gate, not by a runtime counter. A silently
un-engaged MoE run would be indistinguishable from the control in the log. That
is a §1.1 (SILENT) gap in the log line, not in the model — listed in §7.

### 4.2 Six runs, because "green once" cannot decide a race

The gate costs 3-6 s, so it was run **six times**. All six: `1 passed; 0 failed`,
and **all seven two-chunk maxima identical to 7 significant figures**
(`q=2.605e-7 k=1.771e-7 v=3.713e-7 g=4.410e-7 b=2.044e-7 w=2.248e-7
state=1.782e-7`), as were all seven one-chunk maxima.

### 4.3 The verdict, and the three things it is not

**GREEN and reproducible at the two-chunk scope.** BK2 — the sequential reverse
recurrence over chunks, plus the `d_k_bptt` / `d_e_bptt` / `d_s_shift` glue that
`2a430cc` measured at rel 3.3e-1 and 6.2e-1 before its fix — matches an
independent f64 oracle to **4.4e-7 at worst**, and does not move across runs.
**So on the reading `docs/reviews/kda-adjoint-2026-10-01.md` §4 offers as (a) —
f32 conditioning of the instrument, not a race in the kernel — the evidence
lands on (a):** a term that is ~1e-4 of `|L|` is exactly the magnitude this oracle
resolves to 4e-7, so an f32 finite difference of it moving 7-27 % is the
instrument's error budget, not the kernel's.

Stated limits, so nobody reads this as closing more than it closes:

1. **Scope is 2 chunks (T=32), and `d8fa449`'s disagreement is at 16 chunks
   (T=256).** Different scope, and the 16-chunk disagreement is **not** resolved
   by this run — it is only shown to be a scope question, not a broken BK2.
2. **The instrument is an f64 oracle, not a finite difference.** So this run does
   not speak to the precision of the FD instrument itself; it speaks to the
   kernel.
3. **Determinism is measured at the seven printed maxima**, i.e. to 7
   significant figures of an aggregate. Identical aggregates are strong evidence
   and not a bitwise proof of every output element.
4. **BK2-gated does not mean BK2-enabled.** §6 of that review is unchanged: on
   the trainer's backend the fused op *declines*, so the ops path still carries
   the gradient, and nothing here argues for turning the kernel on.

*(§4's verdict is also the answer to the brief's premise that this run "does not
exist": a run of exactly this binary was on the card at 14:43, ~20 min before I
re-ran it myself, and my numbers are independent of whatever that one printed.)*

### 5.2 `--temp 0` does not exist: it panics

```
$ ./target/release/generate --export … --prompt The --steps 120 --temp 0
cannot sample empty range
```

The sampler computes `exp((x - max) / temp)`; at `temp = 0` the winning element is
`0/0 = NaN`, the sum is NaN, and `gen_range` refuses the range. **So the brief's
"temperature 0 (greedy)" cell is not available in this binary**, and the honest
thing is to record the panic rather than substitute a near-zero temperature and
call it greedy. Greedy decode is a one-line branch (`argmax` when `temp <= 0`) in
`crates/dormouse-cli/src/bin/generate.rs:47`; it is the inference owner's call, not
this lane's, and it is listed in §7.

## 6. The wave — per-arm table

### 6.1 The finding that reshaped the queue: four of the six arms could not be set

The first launch attempt was `--set use_mhc=true`, the invocation
`docs/reviews/mhc-2026-09-30.md` and AB row 7b document. It died in **32
seconds**:

```
train failed: unknown config key "use_mhc"
```

**`--set` is not a serde override. It is a hand-written `match`**
(`crates/dormouse-core/src/config/override.rs:28-71`) listing 33 keys, and
`use_mhc`, `mhc_streams`, `use_situ` and `use_attnres` are **not on it**. The
config *fields* exist in `schema.rs` and the arms are wired into the model; the
trainer's seam that turns a command-line string into a config value was never
extended for them. So the four documented invocations
(`--set use_mhc=true`, `--set use_situ=true`, `--set use_attnres=true`,
`--set use_kda_rope=true`) **have never reached a trainer process.** Two of the
six arms' flags *are* on the list — `moe_topk`, `aux_fb_weight` — which is why
this went unnoticed for a week: the two arms that were documented as runnable
were the two that worked.

This is the ADR-0011 LOUD class doing its job (the refusal named the cause and
the escape), and §1.7's document-vs-code disagreement class. The fix is six lines
in `override.rs`; **it is not this lane's to make** (§1.6: do not edit files
another lane is in), so it is a follow-up in §7 with the file:line.
