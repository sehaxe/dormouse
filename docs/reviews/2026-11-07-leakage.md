# 2026-11-07 — Leakage audit: can the model see the byte it must predict?

Hostile read of the **current** training path — `block_form="transformer"` and
`block_form="kda"`, dense FFN and the expert bank — plus the data readers, the
doc-masking arm and the eval window. The question is not "does the loss go down"
but "is the number the loss is compared against held out at all".

The class of defect is the one the Muon audit found in another instrument
(`docs/reviews/2026-11-07-muon-audit.md`): **a measurement that quietly lies.**
For a byte-level LM the expensive instance is target leakage — any path that
lets the model see `x[t+1]` while scoring position `t` gives the loss a floor it
did not earn, and every architecture A/B afterwards compares two wrong numbers.

**VERDICT: the current path is causal and target-disjoint. Two latent
eval/train overlap holes were open in the *configuration* seam (not in the
model); both are now refused loudly. One instrument duplicate and one measured
content overlap are reported, neither flatters a current run.**

Instrument: branch `leakage` (worktree `dormouse-wt/leakage`), baseline `0c63c20`, fix in this commit,
CPU only (`CUDA_VISIBLE_DEVICES=""`), torch 2.13.0+cu129, one thread. Gate file:
`port/tests/test_leakage.py` (31 tests). The KDA arm runs its **COUNTED causal
SDPA fallback** on CPU — FLA's `chunk_kda` is CUDA-only (`fla_status` returns
`device cpu: FLA kernels are CUDA-only`), so the fused arm's own kernel is
outside this gate; see "What this does not cover".

## The mechanism, one line each

**Shift (1).** `_windows` (`data.py:77`) is the only definition:
`ids = raw.view(batch, seq_len+1); x = ids[:, :-1]; y = ids[:, 1:]`. The targets
are read by the loss and by nothing else — the model's `forward` signature takes
them only to compute CE (`model.py:635`), and every aux head is built from
`input_ids` (`dspark.py:262`, `mtp.py:331`, `jepa.py` has no ids). Gate 1 is
therefore two assertions: `y[:, :-1] == x[:, 1:]` (a reversed or same-position
shift fails), and changing `y[p]` leaves **all** logits bit-identical (any
teacher-forcing of the label sequence fails).

**Causality (2).** Transformer: `F.scaled_dot_product_attention(..., is_causal=True)`
(`transformer.py:212`). KDA one-shot: the same (`kda.py:680`); the segmented
KDA path uses an explicit `cols <= rows` mask (`kda.py:691`), whose diagonal is
at `tp` — the gate pins that exact matrix. Everything else in the block is
per-position: the controller reads `[ctx ; h0]` at the same position
(`loopblock.py:1095`), the Engram keys fold the **current and earlier** bytes
(`engram.py:115-145`), and the MoE router is per row.

**Doc masking (4).** `DocPackedStream._row` (`data.py:606`) puts ONE document in
a row: a whole short document (mask `[:remaining-1]`, tail padded) or a
contiguous chunk of one long document (mask all `seq_len`, the extra read is the
last in-document target). The gate re-derives the boundary from the real
sidecar and checks every scored target: `target < b`, `target ∉ starts`. The
eval reader (`MaskedByteStream`, `data.py:760`) keeps the flat geometry but
drops a target at a document start or at the ring seam.

**Eval (5).** Same-file mode: `hi_train = size - eval_bytes`, `ev.lo = hi_train +
eval_offset`, so the ranges touch and never overlap. `eval_data` mode and
`mix_plan` mode are different files and were **trusted**; that is F1/F2.

**Sampler (6).** `_unit(seed, step)` (`mixture.py:329`) is splitmix64 over
`(seed, step)`; `source_for_step` is a cumulative draw over the stage weights;
`shard_order` is a seeded Fisher–Yates. No global RNG, so two runs with one seed
read the same batches, and a resume lands on the draw an unbroken run would
have made.

## Findings

### F1 — CRITICAL-if-hit, FIXED: `eval_data` was trusted to be a different file

`open_streams` (`data.py:1030`) applied the no-leak split **only when
`eval_data` was empty**. With `--eval` set, the train stream read
`[0, size)` of `data` and the eval stream read `[eval_offset, eval_offset +
span)` of `eval_data`; nothing compared the two identities. `--data x --eval x`
trained on the whole file (including the eval window) and scored it. The same
hole existed for a `mix_plan` source.

Evidence, `test_eval_data_naming_a_training_file_is_refused`: a 1 MiB file
named as both, eval window 65 536 B → the helper returns
`leaked = 512 × 2 × 65 = 66 560 B` (the whole eval read span), and `train()`
now raises `LoudError: eval/train overlap: 66560 B …`.

**Fix (safe, loud):** `eval_train_overlap` (`data.py:975`) maps the eval read
span and every training file's byte range by `(st_dev, st_ino)` — the only
honest identity, since two paths can name one file — and `train()`
(`loop.py:1171`) refuses when the intersection is non-zero, naming the file and
the exact bytes. Unknown streams (a caller's test double) answer `[]`; the gate
never invents a range. No shipped config hits it (all pass an eval file that is
not a source), so no recorded number moves.

### F2 — CRITICAL-if-hit, FIXED: `mix_plan` + `eval=true` with no `eval_data`

`open_streams(run, eval_only=True)` carves the eval tail out of `train.data`;
the mixture reads every planned source in full. If `train.data` is also a plan
source (exactly the night recipe's shape: `--data data_local/best/fwedu.bin`
plus `mix_plan=configs/mix_v7*.toml`), the eval tail is trained on. The night
scripts avoid it by passing `--eval data_local/mix4/web_eval.bin`; a forgotten
`--eval` would not have been loud.

Evidence, `test_a_mix_plan_with_an_eval_tail_of_its_own_source_is_refused`: an
8 KiB source, one-stage plan, `eval_batches=4` → `leaked = 512 B` (the carved
tail is the full `4 × 2 × 64` eval window) and `train()` refuses.

**Fix:** F1's gate covers this shape too (the eval stream is built from
`train.data`, and `train_file_ranges` knows the plan sources).

### F3 — MINOR, not fixed: the same-file eval re-scores `batches × batch` bytes

`open_streams` reserves `eval_bytes = batches × batch × seq_len` bytes at the
tail, but the eval reads `batches × batch × (seq_len+1)` — one successor byte per
row. At the flagship geometry (24 × 8 × 1024, `eval_bytes=196608`) the last
**192 bytes wrap to the eval head**: 192 positions are scored twice and the same
192 tail positions are never scored. `over 196608 B` is therefore 192 positions
short of distinct. This is an instrument duplicate, not a train leak (the bytes
are eval bytes both times).

Effect bound: `192 / 196800 = 0.098 %` of positions; if the duplicated head and
the missed tail differed by 8 BPB the flattery would be **0.0078 BPB**, at a
realistic ~2 BPB it is **0.002 BPB**. Left as is because changing the carve
moves the boundary for every same-file eval on record (the `test_bpb_accounting`
pin asserts `lo == size - 65536`); the night runs use a separate eval file and
do not take this path.

### F4 — MINOR, measured, not a code defect: content overlap with the training sources

Different files can still contain the same bytes. Measured on the real night
config (`mix_v7.toml` sources vs `data_local/mix4/web_eval.bin`, eval window
`[0, 196800)` at batch 8 × seq 1024):

* method: 1024 random printable 64-byte windows from the window; locate each in
  every source (`rg -F`), map back to the eval offset, extend the exact match in
  both directions, union the runs. This finds **verbatim ≥64 B** overlap, not
  edited near-duplicates (it is a lower bound on content overlap, and a minimum
  run length is the price of a 22 GB scan).
* result: **2 241 B of 196 800 = 1.14 %** of the held-out window has an exact
  match in a training source. By source: fwedu 1 688 B (max run 414 B),
  finemath 730 B (235 B), science 378 B (378 B), math 101 B (101 B), cosmo / ru /
  code / wiki_ru / instruct 0 B. **No document-sized duplication**: the longest
  verbatim run is 414 B, against 400 B–120 KB documents in `fwedu.bin`.
* interpretation: FineWeb-Edu (`best/fwedu.bin`) and the mix4 web carve
  (`web_eval.bin`) are both Common Crawl descendants; the overlap is shared web
  paragraphs, not the same document re-labelled. Upper bound on flattery if the
  model memorised all of it: `1.14 % × 8 BPB = 0.091 BPB`, realistically
  `≈ 0.02 BPB`. **At the current budget it is 0**: 2 000 steps × 3 accum × 8 ×
  1 024 = 49 MB over 22 GB, i.e. the sources are read **0.002 epochs**; the
  40 000-step chain reads **0.044 epochs**. The model has not seen those bytes.
  This becomes worth a decision only for a run that reads `fwedu` past one
  epoch; the launch recipe is 4 epochs max (`max_epochs=4.0`).

### F5 — not a leak on the flat stream; refused where it would be

The capacity-padded MoE (`moe_capacity > 0`, the **default 1.0**; `arch_moe8`
does not override it) keeps the first `cap` assignments per expert in flattened
token order (`experts.py:2044-2048`), so a row's kept/dropped set depends on the
rows before it in the batch. On the **flat** stream that is still causal — the
rows of one batch are consecutive bytes of one source, so "before in flat order"
is "earlier in the stream". The gate is therefore `atol=1e-5` on the MoE arm for
a tail edit (the routed gather's row count, and hence its GEMM tiling, changes;
measured max 4.8e-7), against O(0.1) for an unmasked triangle.

With **doc masking** the rows are independent documents, so that coupling would
be false context — and `config._validate_doc` already refuses
`doc_masking=true` with `moe_topk>0 and moe_capacity>0` (`config.py:4354`).
Verdict: no fix, and the existing refusal is load-bearing; do not "optimise" it
away.

### F6 — documented, not a defect: the readers are periodic per epoch

`ByteStream._refill` wraps `hi → lo` (`data.py:379`) and `ShardStream` wraps the
seeded order (`data.py:251`), so epoch 2 is epoch 1 byte for byte. That is the
documented behaviour (the class docstrings say so), the gate pins it, and the
repetition is capped by `max_epochs` (default 4, `mixture.py:124`). The
mixture's **source draw** is not periodic: `source_for_step` keeps drawing from
`(seed, step)`, so a second pass over the step budget gets a different source
order; `test_the_mixture_does_not_replay_its_source_draw_next_pass` pins that.

## What this does not cover

* **The fused KDA kernel.** CPU-only: `fla_status("cpu") == (False, "device cpu:
  FLA kernels are CUDA-only")`, so every KDA test above runs the COUNTED
  `kda_sdpa` fallback — the same wrapper, controller, Engram and CE, but not
  `fla.ops.kda.chunk_kda`. The fused arm's causality is FLA's contract; the
  wrapper's own contract is that `carry=False` passes no state and takes the
  one-shot branch (`kda.py:562-568`), and the fallback's explicit mask is pinned.
  A GPU gate that captures `chunk_kda`'s attention is owed; it cannot run here.
* **Edited near-duplicates.** F4 finds exact ≥64 B runs; a document with a
  changed sentence is invisible to it. The honest claim is the measured lower
  bound, not "no overlap".
* **Other corpora.** The real-sidecar gate reads `mix4/code.bin`; the SFT and
  RL lanes are outside this training path.
* **The `transformer` arm's MoE FFN.** The vanilla form has its own GELU FFN
  (`transformer.py:131`); `n_experts` is a KDA-loop knob. The transformer arm is
  therefore gated dense, and the MoE FFN is gated on KDA, where it lives.
