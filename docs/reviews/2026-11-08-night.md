## 2. The suite: 22 red -> 0

`CUDA_VISIBLE_DEVICES="" pytest -q` over **2 194 tests: exit 0** — three runs;
the last one after every edit of the night.

The starting "22 red" was mostly tests calling their own fakes with an old
signature, plus my own regressions. The seven that remained were reclassified by
`docs/reviews/2026-11-08-fused-cluster.md`:

* **Five skip without CUDA.** The "7 red CPU suite" was a card-visible run.
* **One was a real code defect**: the fused AdamW writer forms its bias
  correction from `_adamw_t`, and torch's own `step()` advanced each parameter's
  counter but not that one — so a capture fallback resumed at a stale `t`
  (3.1e-05 at `embed.weight` with the losses equal to nine digits). Fixed, with
  a two-arm CPU gate that fails on the old line.
* **One was a flaky fixture** (unseeded RNG + a controller that can read exactly
  zero), **one a stale counter test** (asserting a bf16 counter on an fp32
  store), **one a stale tolerance** (gradients held to 1e-6 where the module's
  own rule is 5e-5), **one patched a function its path never calls**.
* The other real defect found on the way: `_fall_back` handed the Muon group the
  AdamW LR for the next step (`1/mult` of its own), because it restored the WSD
  float into every group. Fixed with a CPU gate.
* **The last two card gates found a defect in themselves.** Their launch counter
  matched `cudaLaunchKernel` only; a Triton kernel launches through the driver
  API as `cuLaunchKernelEx`, so the fused arm read as **zero launches** and the
  "drop" was 11 vs 0 — true, and measuring nothing. All three names counted:
  **fused 2 vs eager 11** per KDA iteration, **49 vs 804 (16.4x)** per residual
  chain. Both gates pass with real numbers.

Also closed from the audits: the LayerRoPE `exp` bound (with a device tally),
the WSD decay window, the KDA SDPA `F.normalize` epsilon, and the `norm_eps`
misclassification (it is live on the dense form — through the FINAL norm, not
the blocks; measured 0.20 logit shift at 1e-3 -> 1e-1).

## 4. The 1M question

`docs/research/2026-11-08-long-context-eval.md` answers it in the order that
matters:

* **No artifact on disk can run a 1M test.** `flagship3` is a 1K dense control
  with no CSA; the one trained CSA checkpoint (`longctx1`, 102.7M, 8K) died with
  the corpus.
* **No 95M long-context result exists in the literature.** The closest measured
  points are 300M Infini (passkey collapses past 4-8K), 0.5B SRRM, and 1.24B
  Llama-3.2-1B in HELMET (2.0 ∞Bench, 24.6 HELMET at 128K).
* **NIAH correlates with real tasks at rho 0.44-0.76**, so retrieval evidence
  buys a MECHANISM claim: "exact retrieval at 1M", not reasoning.
* **The protocol**: gates A (artifact) -> B (state carry) -> C (rank probe) ->
  D (S-NIAH-8, 100 items, exact match, five controls), pass at 95/100 with a
  Wilson lower bound of 88.8%, 3-12 GPU-hours.
* **The state number was wrong**: 33 MiB is ONE CSA slot; the loop carries one
  per iteration. 3 slots = 99 MiB, a 12-layer stack = 396 MiB. README and the
  site now say that, and the site lists both corrections as retractions.

The runner is built (`port/scripts/niah.py`, seven CPU tests, `--dry-run`
verified) and refuses the only on-disk checkpoint by design. The artifact is one
command away: `port/scripts/train_csa8k.sh` (8K window, 102.7M, 3 h 50 m for 8k
steps at the previous run's measured rate).

**Verdict: one candidate, and it is not yet a result.** The combined arm is
0.0128 BPB better than control — at the top of the noise band, from ONE seed,
and larger than the sum of its five parts (−0.0039). That pattern is either an
interaction or a lucky seed; a single-seed 0.013 does not separate them. The
individual arms are all inside the band and two are worse (dropping RoPE on two
layers costs +0.005, the attention gate +0.003). The honest next step is a
2-3-seed control-vs-all A/B at this budget, not a longer run of "all".

The control's 1.4906 at 120 MB is the first number on the refetched corpus; it is
**not comparable** to the old 1.4946 at 250 MB.

**What 1.4906 means, on the same bytes.** The arms score the first 196 608 B of
`fwedu_eval.bin`; general-purpose compressors on exactly those bytes get
**bzip2 -9 2.5878**, **xz -9 2.7134**, **zstd -19 2.7703** bits/byte. The model
— after 120 MB of training, against compressors that saw nothing — is **1.10
b/B below the best of them**. That is the comparison the BPB is for; it is not
a claim about intelligence, and the compressors are not tuned per-domain.

## 5b. The CSA artifact: trained, gated, and it does NOT earn a 1M claim

`train_csa8k.sh` ran 8 000 steps in **1 h 59 m** (faster than the 2026-10-27 run's
7 h 38 m — the card was free and the corpus was in page cache). 102 678 928
params, 8K window, six-source mixture, final train loss 1.2516, eval **BPB 1.900**
on 32 768 B at 8K (4 x 1 x 8192; not comparable to the 1K-window dense number).

**The artifact is compromised, by my command, not by the code.** The loader
refused it loudly: `lfb_bias range [-95.162, +56.517] is past ±10: this controller
DIVERGED` — the legacy `moe_lb_mode="sign"` arm, whose collapse was measured and
written up on 2026-11-04 (`docs/reviews/2026-11-04-routing-collapse-CONFIRMED.md`:
`sign` winds without a bound, 9 of 512 experts live). I copied `longctx1`'s
2026-10-27 command, which predates the fix. `train_csa8k.sh` now pins
`moe_lb_mode="prop"` (bounded at ±2, the arm the collapse review measured) and a
corrected run is on the card.

The protocol ran anyway, because a refused claim is a result:

| gate | result |
|---|---|
| A artifact | **PASS** — `use_csa=true`, `csa_gate` live in 1/1 slots, `max_seq_len=8192`. A 1M pass needs `--allow-beyond-window` (a named length-generalization test; the loop form has no absolute position table and carries KDA/CSA state) |
| B carry | **PASS under the scale-free rule.** 1 pass vs 2x512 B: `dloss` 1.05e-05 nats, the 8 answer bytes identical, global argmax 99.7%. The protocol's absolute 1e-3 logit bar is not scale-free: it is 4e-3 of a ±32 logit scale, i.e. bf16 rounding. Gate B now reads `dloss` + the 8 answer bytes and prints the rest |
| C rank | **FAIL** — the selector's rank for the needle chunk is ~119 of 128 at the default (max) distance: chance. Gate D was **not run**, per the protocol |

**Gate C's failure is a position effect, and that is the useful finding.** Same
model, same 976-byte distance, needle near the window START (context 1024) →
median rank 119, 0/10 in the top-32. Move the window to 2048 so the same needle
sits mid-document → median rank 17.5, 7/10. At shorter distances in a 1024-byte
window it also works (64 B: median 8, 7/10; 512 B: median 10.5, 8/10; 832 B:
median 31.5, 5/10). So the selector is not distance-limited at 1K; it does not
select a needle that sits in the first ~50 bytes of the window — which is exactly
where the protocol's default (max distance) puts it.

Consequence for the protocol: gate D must run the needle at a MID-window
position as the primary condition and treat "needle at the very start" as its
own, separate condition. The default distance is the one place the model is
weakest; quoting it alone would understate or overstate depending on direction.

**No 1M retrieval number is claimed tonight.**
