# 2026-11-04 — контроллер починен: 9 → 313 живых экспертов

## Замер (2000 шагов, свежий прогон, bucketed-диспатч)

| | было (150k шагов, `sign`) | стало (2k шагов, `prop` γ=0.001, кламп ±2) |
|---|---|---|
| живых экспертов | **9 / 512 (1.8%)** | **313 / 512 (61.1%)** |
| максимальная доля | **50.0%** | **2.6%** |
| top-10 | **100%** | **15.2%** |
| bias | −218 … +72 | ровно ±2.000 (кламп) |

Приёмка была: живых ≥80%, top-10 ≤30%. **top-10 пройден с запасом (15%), живых 61% — нет.**
Кривая ещё растёт (297 @1k → 313 @2k), но упирается в кламп: bias стоит ровно на ±2.000,
то есть контроллер работает на пределе и не может двигать дальше.

Идёт второй арм: `γ=0.002`, кламп ±4.0 — если он даёт ≥80%, рецепт фиксируем там.

## Важная поправка про «8.6×»

Мои слова «все прогоны шли python-циклом по экспертам» — **неверны**. Живые прогоны
использовали `moe_triton_gemm` (видно в каждом log-срезе: `moe_triton_gemm=300`),
а цикл — это `_naive_dispatch`, который в наших конфигурациях не вызывался.

Реальные числа с карты (m400, fwd+bwd):

```
naive    1111 ms   ← не наш путь
triton    124 ms   ← наш путь
batched   129 ms   ← новый, чуть медленнее triton
```

То есть **8.6× — это naive→batched, а triton уже был быстрым**. Переход на batched/bucketed
не ускоряет текущий прогон; он даёт (а) отсутствие python-цикла как класса, (б) bucketed-банк,
который не падает по памяти при любом роутинге, (в) 8.6× для конфигураций, где triton
недоступен. Скорость шага надо искать в другом месте (это отдельная задача).
