# Metrics audit — every number the trainer prints, recomputed

2026-11-07 · commit `a80854d` (`79331e4` is the eval-weighting fix already on
main) · CPU only (`CUDA_VISIBLE_DEVICES=""`, torch 2.13.0+cu129) · worktree
`/home/sehaxe/dormouse-wt/metrics`, branch `wt/metrics`.

The Muon audit (`2026-11-07-muon-audit.md`) showed that four "different"
defects were one class: **the number the run optimised was not the number the
instrument measured.** This audit recomputes each printed number from its own
definition, names the reduction, and records where the two disagree. The new
gates are `tests/test_metrics_audit.py` (9 tests), the updated
`tests/test_eval_tail_cap.py`, and the existing
`tests/test_invariants_eval.py` (main, `79331e4`).

**Verdict in one line:** the BPB arithmetic and `bytes_seen` are exact after
the `79331e4`/this-branch fixes; `tokens_per_s` is a correct per-window rate but
overstates whole-process throughput by **10.96 %**; the dense arm's FLOP claim
is **5.03× too low** and its ledger was **4.4 % high**; two counters are not
functions of the config (`moe_expert_calls`, `moe_shared_forwards`), and one
attention label says `kda` while the KDA arm did not run.

## 1. BPB — exact reductions and independent values

For one eval batch, write `p(y_j | x_j)` for the head's softmax at target
position `j`, `N_b` for the positions batch `b` scores (the mask sum, or
`batch × seq_len` flat), and `B` for the number of batches.

| printed number | exact reduction | independent value | logged value | verdict |
|---|---|---:|---:|---|
| `fin` / `bpb_fin` | `(1/B) Σ_b (1/N_b) Σ_{j∈b} −ln p(y_j)`; divide by `ln2` for BPB. Equals `Σ nats / (ln2 · Σ N_b)` when every batch has the same `N_b`. | `6.544371198` | `6.544371198` | **exact** (Δ 0.0, fresh KDA `max_iter=3` checkpoint) |
| `bpb_mean` | `(1/B) Σ_b [ (Σ_{i=1..T} mean_j −ln p_i(y_j) + mean_j −ln p_fin(y_j)) / (T+1) ] / ln2` | `6.105966095` | `6.105966095` | **exact** (Δ 0.0, same checkpoint) |
| `bpb_fin` (masked) | same, with `N_b = mask.sum()` per batch | `8.762180919` | `8.762181006` | **holds**, Δ `8.7e-8` (float32 sum order) |
| `bpb_mean` (masked) | same, every readout masked and byte-weighted | `9.031820713` | `9.031820539` | **holds**, Δ `1.7e-7` |
| `scored` (masked) | `Σ_b mask.sum()` | `252` | `252` (`masks [128, 124]`) | **holds** |

The checkpoint row is a real save/load: 2 CPU steps, `max_iter=3`, then
`load_ckpt` + `load_model_state`, then the independent read recomputes every
head call from its logits. `per_iter` on that fixture is
`[4.480308, 4.042493, 3.870320]` nats and `fin = 4.536212`: `fin` is the
**(T+1)-th head call** (the final mean readout), not the last per-iteration CE.
That is the readout generation uses: the decode forward
(`model(x, targets=None)`) returns logits that are **bit-identical** to the
final head call (`torch.equal` true, max|Δ| 0.0). `eval_row` writes
`"bpb" = bpb_fin` and keeps `"bpb_mean"`/`"loss"` separate (`loop.py:1101-1103`).

**What was broken and is now fixed on main (`79331e4`):** a doc-masked eval
averaged per-batch means, so a batch that scored 123 positions weighed the same
as one that scored 125. The independent byte mean differed by **0.00332 BPB**
on the invariants fixture (`2026-11-07-invariants.md` EV-2); `_eval_loss` now
weights every mean by that batch's scored positions (`loop.py:937-960`). The
flat path is unchanged because its weights are constant. Our gate recomputes
the same identity from the head's logits to `1e-6`, not `1e-5`.

**Tail-cap denominator (fixed here).** Above the 1 MiB eval-tail cap the stream
wraps and scores some bytes more than once. The old code replaced `scored`
with the **distinct** byte count while the mean still divided by the
**predictions** it summed (`loop.py:961-968`). That is two different sets in
numerator and denominator. The denominator is now the prediction count, and the
line prints `eval_tail_capped=req/granted distinct=<unique>` so the two are not
confused. Gate: `tests/test_eval_tail_cap.py`.

**Padding.** `DocPackedStream` passes `mask=0` for padding and a document's
last byte; `masked_ce_mean` uses `(ce·mask).sum()/mask.sum()`, so a padded
position is excluded from **both** sides. `_eval_loss` uses the same mask for
`scored` and for the numerator. Verified by the masked row above and
`tests/test_docmask.py::test_masked_loss_ignores_padding_and_boundary_targets`.

## 2. `bytes_seen` — product, staged sampler, resume

The one definition is `tokens_per_step = batch × seq_len × grad_accum` and
`bytes_seen = step × tokens_per_step` (`loop.py:1350`, `:1098-1100`). It is
optimizer-step arithmetic, so `grad_accum` is included; the run event carries
the same `bytes_per_step`.

| case | independent product | logged | verdict |
|---|---:|---:|---|
| single file, 200 steps, b8 s128 g3 | `200×8×128×3 = 614 400` | `614 400` | **holds** |
| single file, 4 steps, b2 s64 g3 | `4×2×64×3 = 1 536` (per step 384) | `384/768/1152/1536` | **holds** |
| resume at step 5 (checkpoint at 3) | `5×2×64×3 = 1 920`, then 2 304 | `1920, 2304`; no rows 1–4 | **holds**, no re-count |
| `mix_plan`, 3 steps, b2 s64 g2 | `3×2×64×2 = 768` | `256/512/768` | **holds** |
| `mix_plan` resume at step 5 (checkpoint at 3) | `5×2×64×2 = 1 280`, then 1 536 | `1280, 1536` | **holds**, replay skips 4 opt steps × g2 |

The mixture is built for `steps × grad_accum = 6` micro-batches
(`loop.py:1175-1180`), which is the unit its stage schedule and epoch cap use;
passing `steps` alone ran the mix `grad_accum`× fast (the comment records that
defect). Resume skips `start × (seq_len+1) × batch × grad_accum` source bytes
(`loop.py:1427`) and the first resumed log continues at `start+1`; the counter
is not re-added.

**Definition nuance, not a failure:** each micro-batch *draws*
`batch × (seq_len+1)` source bytes (the extra byte is the last target). The
counter counts the **scored targets** (`seq_len`), so it is the right
denominator for BPB and the right axis for `runlog.unique_bytes`, but it
understates the corpus cursor by `1/(seq_len+1)` (0.78 % at 128, 0.10 % at
1024). A reader using it as “bytes read from disk” is off by that factor.

## 3. `tokens_per_s` vs wall clock

Run: `configs/audit_d128.toml`, b8 s128 g3, 200 steps, `eval=false`,
`log_every=200`, CPU, external `date +%s%N` around the process.

| quantity | value |
|---|---:|
| tokens (target positions) | `200×8×128×3 = 614 400` |
| external wall clock | `37.237 s` |
| external rate | `16 499.7 tok/s` |
| logged `tokens_per_s` (one 200-step window) | `18 308.3 tok/s` |
| internal loop time implied by the log | `33.559 s` |
| gap, logged vs external | **+10.96 %** |
| process overhead (import, model build, data open, teardown) | `3.68 s` = 9.9 % of external |

The per-window instrument is correct: its denominator is the interval between
log cadences, and `StepTimer.window_s()` reads before `timer.report()` resets
the mark (`loop.py:2018-2029`). The number is **not** a whole-run rate: it
starts after model build and excludes process startup/teardown, so a dashboard
quoting it as wall-clock overstates throughput by ~11 % on this run. On a GPU
run the same gap is smaller in absolute seconds but still nonzero; the honest
run-level number is `tokens / (process wall clock)`.

## 4. FLOPs per byte — the dense arm is not compute-matched

`configs/flagship3_dense.toml` (12 layers, d=832, f=3072, V=256, b1 s1024,
95 035 200 instantiated params). `FlopCounterMode` measured a real
forward+backward at b1 s1024 and b1 s256; it counts **matmuls only** on CPU (the
`aten.mm` lane; SDPA is not in its CPU registry). The analytic body+head bill is
therefore compared to the measured matmuls, and the T-dependent attention core
is added explicitly.

| quantity | formula | value (MFLOP/byte, fwd+bwd) | verdict |
|---|---|---:|---|
| block (qkv+proj+MLP) | `3 × 2·L·(4d² + 2df)` | `567.410` | matches measured |
| attention core | `3 × 4·L·T·d` | `122.683` at T=1024 | omitted by the CPU counter |
| head | `3 × 2·d·V` (dense) | `1.278` | matches measured |
| **measured matmuls** | `FlopCounterMode`, b1 s1024 | **`568.689`** | `body+head` exact |
| measured + analytic attention | `568.689 + 122.683` | **`691.372`** | **corrected ledger** |
| old `mod_ledger` total | `3·(24·L·d² + 4LTd + 2dV)` | `722.043` | **+4.43 % high** |
| config comment's claim | `6·94.6M / 4.485` | `126.555` | **5.46× too low** |
| old flagship pin | measured, `control-transformer.md` | `137.420` | dense/old = **5.03×** |

The `FlopCounterMode` raw-vs-ledger ratio is `568.689/722.043 = 0.7876`, but
that is the **instrument's blind spot**, not a model defect: the measured
matmul bill equals `3·(block+head)` to display precision, and the only missing
term is SDPA. On a GPU with a flash/efficient SDPA kernel the same counter
registers that term (`flop_counter.py:313-316` registers only the
`_scaled_dot_product_*` kernels, not the composite math path). The T-dependence
was checked at T=32 and T=64 in `tests/test_metrics_audit.py`; omitting it or
adding a spurious `T²` term fails.

**Corrections:**
- `port/scripts/mod_ledger.py` transformer block is now
  `2·L·(4d² + 2df)`, not `24·L·d²` (the latter is the `f=4d` special case and
  overprices this `f=3072` arm by 4.43 %). The TSCT head is priced
  `2(d·r + r·V)` when `use_tsct`, not the dense `2dV`.
- `port/configs/flagship3_dense.toml` comment now states 691.37 MFLOP/byte and
  5.03× the old flagship, and points at `port/scripts/mod_ledger.py` (it named
  `scripts/flops_ledger.py`, which is not on this branch).
- Gate: `tests/test_metrics_audit.py::test_the_transformer_ledger_includes_the_t_dependent_attention_core`.

**Consequence:** the "at or below the old flagship's 137.4" sizing note and the
`docs/reviews/2026-11-06-control-transformer.md` comparison are not
compute-matched. The dense arm costs ~5.03× the old flagship's FLOP/byte; any
dense-vs-KDA quality comparison must carry that ratio, or it is comparing a
larger compute budget.

`kda=` is not a counter; it is a derived label (`loop.py:101-111`). With
`attn_kind="full"` it prints `kda=full,n=3` while the KDA arm did **not** run
(`kda_sdpa` absent, `attn_full_forward=3`). It is an attention-arm label, not a
KDA count; a reader who takes the field name literally is misled. The two
counters in bold above are the lying instruments; `moe_expert_calls` also only
exists on the CPU/reference dispatch, so on a CUDA banked run the field is
absent rather than zero.

Gate: `tests/test_metrics_audit.py::test_the_predictable_arm_counters_equal_their_config_formula`
and `::test_moe_expert_calls_is_data_dependent_and_only_on_the_naive_path`.

## 6. KDA `max_iter=3`: fin vs mean, and the consumers

For the KDA form, `bpb_fin` is the **final mean-readout** readout (`fin`), the
`(T+1)`-th head call; `bpb_mean` is `(Σ_{i=1..T} CE_i + CE_fin)/(T+1)`. They are
not the same number even on a trained checkpoint: the fixture above reads
`per_iter=[4.4803, 4.0425, 3.8703]`, `fin=4.5362`, `bpb_fin=6.5444`,
`bpb_mean=6.1060`. Generation reads the final readout, bit-for-bit (above).

**Consumers on main:**

| consumer | reads | verdict |
|---|---|---|
| `port/scripts/dashboard.py:283-292` | `bpb_fin`, else legacy `bpb` with `_ev_kind` flag; `:322` plots only fin rows; `:851-864` labels the axis | **correct** |
| `port/scripts/collect_ab.py:20-45` | regex `bpb_fin`; refuses legacy `bpb=` and mixed files | **correct** |
| `port/scripts/compare_stairs.py:30-52` | `bpb_fin`; refuses a file with both shapes; refuses a cross-metric stair at `:112` | **correct** |
| `port/scripts/ab_byteflow.py:175` (shared `read_run`, imported by `ab_attn`, `ab_cheapwidth`, `ab_csa`, `ab_docmask`, `ab_engram_ram`, `ab_layerrope`, `ab_longctx`, `ab_mhc`, `ab_mhc_attnres`, `ab_multiblock`, `ab_prelude`) | `evals[-1]["bpb"]`, no `bpb_fin` check | **legacy-unsafe**: on current rows `"bpb"` is `bpb_fin`; on a pre-2026-11-06 JSONL it was the depth mean |

a shared refusal would touch ~30 scripts and their synthetic fixtures. The

`bpb_fin`; it is reported here rather than half-applied.

## 8. Limitations / provenance

- **The 2026-11-05 `final_dense` checkpoint does not reproduce its logged eval
  on current main.** `dormouse eval --out-dir checkpoints/final_dense
  --ckpt-name final_dense --device cpu --eval-batches 1` reads **8.239 BPB
  (fin)**, while `~/logs/final_dense.jsonl` step 50 000 reads `1.848` BPB. The
  snapshot predates loop changes after 2026-11-05 (e.g. `acb013f`'s fused
  epilogue, `0dea6da`'s KDA kernels); the cause was **not isolated** and is a
  checkpoint/commit-provenance question, not an arithmetic one. All BPB gates
  above use a checkpoint written and loaded on the same commit.
- `FlopCounterMode` on CPU counts only `aten.mm`; SDPA is absent. The measured
  number is therefore the matmul bill, and the ledger adds the analytic core.
  On a GPU with a registered flash/efficient SDPA kernel the counter includes
  it; do not compare a CPU number to a GPU number without naming the backend.
- The `bytes_seen` definition is scored targets, not source bytes read
  (`seq_len+1` per row); see §2.
- `tokens_per_s` is a loop-window rate, not a process rate; see §3.
