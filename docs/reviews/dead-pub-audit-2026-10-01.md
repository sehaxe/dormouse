# The dead-`pub` audit: 411 items, 2 dead, ~2 100 lines of over-visibility

**Snapshot `db64923`, 2026-10-01. Tool: `tools/dead_pub_audit.py` (stdlib only,
one pass, no cargo). Nothing was deleted.**

## The headline the owner asked for

"Cut hard, but cut on evidence." This is the evidence, and the answer is not the
answer anyone wanted: **there is almost nothing dead.** Of 411 `pub` items across
our 23 crates, **2 are dead outright — 60 lines.** The real finding is a
different one, and it is worth more than the deletion would have been:

| verdict | items | lines | what it means |
|---|---:|---:|---|
| `live` — a caller outside its own file | 287 | 7 210 | nothing to do |
| `needs-eyes` — the name is shared by another item | 32 | 292 | cannot be called dead by name search; see §4 |
| `demote` — reached only from its own file or a test | 87 | 2 085 | **`pub` is over-visible; the body is live.** The cut here is `pub` → `pub(crate)`, ~60 characters |
| `cfg-only` — no caller in the *default* feature set | 2 | 21 | a note, not a death (NOISE (c)) |
| `dead-documented` | 1 | 12 | named in a doc, called by nothing |
| **`DEAD`** | **2** | **60** | no code caller, no doc mention, no test |

**The scale-down of "масштабное урезание": the honest number is 60 lines of dead
code, not thousands.** Everything else is either load-bearing or a visibility
label. §7 says where the mass actually is — and it is not in `pub` items.

## Method, and the four ways it can be wrong

`tools/dead_pub_audit.py` finds every `^pub fn|struct|enum|trait|const` at
column 0 (top-level API only; `impl`-block methods are indented and are counted
through the type or trait name that carries them), then looks for that name in
every `.rs` file in the repo — the 6 workspace crates *and* the 20 library
crates, plus `vendor/dormouse-fused/{bench,benches,tools}` and our own `tools/`.
`vendor/cubecl-fix` and `vendor/cubek-fix` define none of ours but are read as
callers. One name-search pass per file; ~5 s cold.

A mention is split three ways, because the three answers are three different
verdicts:

- **in another file, in code** → a real caller (`calls`)
- **in its own defining file, in code** → `pub` is over-visible, the body is live
  (`demote`). This split matters: it is the difference between "delete 439 lines"
  and "delete the word `pub`". The first version of this script got it wrong and
  reported `bidiag_host` — 439 lines of Golub-Kahan bidiagonalization — as dead,
  when `host_svd.rs:52` calls it.
- **in a comment** → documented, not called (`dead-documented`)

A self-use *below* the file's first `#[cfg(test)]` is counted as a test use, so
"only the tests reach it" is a visible column and not silently `demote`.

One scope fact worth its own line: **the doc column reads `.rs` comments only.**
A name documented in a `docs/**.md` file is invisible to it — which is why
`cholesky_host_par` reads `doc = 0` although two other audits written the same
day name it (§1). A `.md` mention is corroboration, never a caller.

The four noise classes, named in the script's header:

- **(a) a `pub use` re-export counts as a use.** The `burn-fused` facade
  (`vendor/dormouse-fused/burn-fused/src/lib.rs`, 60 lines, generated by
  `tools/gen_facade.py`) re-exports all 20 crates. **Nothing in either manifest
  depends on it** — the facade is a CI artifact, not a product dependency, so
  for our purposes it is not a caller either way. It is `library-api`, not a
  candidate.
- **(b) trait methods are reached through the trait name.** A `pub trait` whose
  every method has zero direct mentions is normal and is not reported dead: the
  trait itself is the item.
- **(c) `#[cfg(feature = …)]` is a note, not a death.** `cfg-only` means "no
  caller under the *default* feature set". Two items are in that class (§6).
- **(d) a shared name can never be called dead.** `new`, `forward`, `seam_counts`
  appear in several items; every one of them is `needs-eyes`, never `DEAD`. 32
  items, listed in §4.

Two more limits, both erring toward *not* deleting: `cfg_gated` stops at the
first blank line when walking up to an enclosing `mod`, and `item_extent`
brace-balances without parsing string literals. The first makes a gated item read
as live; the second under-counts. Seven probes were checked by hand and all seven
extents match the closing brace exactly.

## 2. Dead-but-documented: 1 item, 12 lines

**DELETED 2026-10-01** — function and doc line together, in the config-seams
lane (`docs/reviews/config-seams-2026-10-01.md`); `grep train_eval_split
crates/ tools/` is 0. The record below is the finding as made.

`dormouse_data::train_eval_split` (`crates/dormouse-data/src/lib.rs:192`) is
called by nothing and mentioned exactly once, at `lib.rs:16`:

```
//! - [`train_eval_split`] returns a stable held-out tail so eval sees unseen
```

**That sentence is false about our own trainer.** The trainer takes an explicit
`--eval` file and streams it separately (`dormouse-data/src/lib.rs:577`, "Stream
over an explicit file list (e.g. a held-out split)"), so the crate-level doc
advertises a function nothing calls and a mechanism the trainer does not use.
This is ADR-0019's shape in prose: **the reader is told an arm ran when it did
not.** Verdict: **delete the function and the doc line together** — the doc line
is the more valuable half of the deletion, because it is the thing that is wrong.

## 4. `needs-eyes`: 32 items, 292 lines — regex cannot decide these

A name shared with another item makes the count an upper bound belonging to all
of them, so none is ever called dead. The heavy ones: `seam_counts` (6 items),
`reset_seam_counts` (6), `ternarize` (2), `quant_format` (2), `pool_stats` (2),
`init_pools` (2), `memory_cleanup` (2), `kda_seam_counts` (2), `eggroll_mutate`
(2), `note` (2), `calls` (2), `reset` (2).

Nearly all of these are counters or resets — a *seam* function, i.e. code whose
only job is to be counted (the exceptions are `ternarize` and `quant_format`,
duplicated quantizer names, not seam counters). The `pub` is deliberate. Do not
read this row as a finding; it is the list of names a name-based audit cannot
resolve, and a
type-based one (`cargo +nightly udeps` / `-Zunused-crate-dependencies`) would.

## 5. `library-api`: legitimately "dead" inside this repo

A technology library's `pub` is a promise to a future caller, not a claim about
today's call graph. These are **not** deletion candidates and the audit says so:

- **`burn-muon-plus::ns_combine_cuda`** (`fused_kernels.rs:89`, 44 lines) — the
  crate's own module doc already states it (`burn-muon-plus/src/lib.rs:53`): *"`ns_combine_cuda` has **no
  production caller**: its only one was the factored NS branch in
  `MuonPlus::orthogonalize`, deleted as unsatisfiable … It is kept because its own
  test in this module still pins the kernel against the tensor-op expression it
  computes."* **This is the precedent for the whole `library-api` class: dead in
  production, pinned by a test, kept on purpose, and said so where a reader will
  find it.** Any future deletion in this repo should either cite this shape or
  give a better one.
- **The `burn-fused` facade** — 60 generated lines, nothing depends on it, and
  that is correct: it is what `tools/gen_facade.py --check` diffs in CI.
- **`burn-es`, `burn-parcae`, `burn-ptrn`, `burn-eggroll`** — whole crates with
  no manifest naming them (§7).

## 7. Where the mass actually is

The `pub`-item cut is 60 lines. The unused *code* is measured differently, and it
is not small:

**Four library crates, 1 388 lines of `src/`, that no product manifest names
as a dependency.** The only manifest that names them is the `burn-fused`
facade's own (`vendor/dormouse-fused/burn-fused/Cargo.toml:85-95`), and the
facade is the CI artifact above, not a consumer:

| crate | `src/` lines | referenced by another crate |
|---|---:|---|
| `burn-ptrn` | 399 | nothing |
| `burn-es` | 345 | nothing |
| `burn-eggroll` | 327 | nothing (one name-only mention, in `burn-es`) |
| `burn-parcae` | 317 | nothing |

That is **23× the dead-`pub` figure**, and it is a whole-crate decision, not an
item decision. `.bulba/plan.md`'s question 4 ("the unwired library, start
deleting now?") is the right question; this audit is one line of its answer.
A fifth, `burn-fused` itself (60 lines), is a CI artifact by design.

`burn-sct` is the other concentration: 593 of its lines sit under non-live items,
533 of them in `host_svd.rs` — a 745-line vendored LAPACK transcription. It is a
library crate with a live CUDA QR consumer, so this is `library-api` again, but
it is the one crate where a reader should look twice.

## 9. What this audit does NOT establish

- **It is a name search, not a type analysis.** `cargo udeps` resolves paths;
  this does not. A `pub fn` reached only through a macro expansion, a trait
  object, or a `#[cfg]` this script does not parse reads as dead. The `demote`
  split exists because that failure mode was observed and fixed once already
  (§3, item 1).
- **`impl`-block methods are out of scope** by construction. The surface a
  type-based tool would find is not measured here.
- **32 `needs-eyes` items are unresolved**, not cleared (§4).
- **It says nothing about dead code with a live caller** — a function called from
  one place that itself is dead. That is a reachability question, and this is not
  the instrument for it.
- **Snapshot `db64923`.** Active lanes are changing these files. Re-run
  `python3 tools/dead_pub_audit.py` and diff; the columns are stable for exactly
  that purpose.

## The one-line answer

**60 lines of dead `pub` in a repo that looks like it has thousands, and the real
unused mass — 1 388 lines across four whole library crates — is not visible to a
`pub`-item audit at all.** Cut the 60, demote the 87 `pub`s, and decide the four
crates as crates.
