## 1. burn-dspark — YES, it runs, and it finds two defects

### 1.1 Does a runnable reference exist?

**YES.**

- **repo** `https://github.com/deepseek-ai/DeepSpec`
- **commit** `005e03b81cec38b7da6399833d609ee89a2587f2` (2026-07-09, HEAD of `main` at fetch)
- **file** `deepspec/modeling/dspark/loss.py`, function `compute_dspark_loss`
- **sha256** `2e91efcaff780eec0748ef3f6f0a31374f119f609c664cc79289fdd922335328`
- **what it covers** the DSpark training objective: masked CE + L1/TV +
  confidence BCE, with the position decay weights, the `+1e-6` denominators and
  the `Optional` confidence head.
- **fetched and run** 2026-09-30, CPU only, `torch==2.14.0+cpu`, single-rank
  gloo process group.

The four vendored files already in the tree
(`crates/dormouse-core/tests/oracle/dspark_{loss,common,markov_head}.py` and
`dspark_qwen3_4b.py`) are **byte-identical** to upstream at that commit —
verified by sha256, all four, this session. So the transcription was already
faithful; what was missing was execution. That is the whole gap, and it is a
smaller gap than it looks.

### 1.2 Did I run it? What does it agree with us on?

Yes. `compute_dspark_loss` is a pure function of six tensors — but not in a
bare interpreter: it calls `dist.get_world_size()` and `add_metric(...)`, whose
default `dp_sum` reduction calls `dist.get_backend()`. A one-rank gloo group
satisfies both and changes no number. Fixture:
`vendor/burn-fused/crates/burn-dspark/tests/fixtures/dspark_loss_oracle.txt`,
8 cases, 9 significant digits, generated by
`tests/oracle/gen_dspark_loss_oracle.py` (which also re-extracts `upstream/`).

**Agrees (green gate, `ce_and_tv_agree_with_the_official_loss`):**

- the **CE term** and the **L1/TV term**, on all 8 cases, at
  `TOL_REL = 1e-5`;
- the position decay `w_k = exp(-k/gamma)` — the fixture's `block7_exact`
  carries a weighted denominator of **3.73521233**, which is the decayed sum
  and not the undecayed 7, so the decay is demonstrably present and measured;
- the all-masked block returns **exactly 0, not NaN**;
- the ceiling case: `draft == target` gives TV **exactly 0** and
  `accept_rate` exactly 1.

**Disagrees (red on purpose, `the_confidence_term_agrees_with_the_official_loss`):**

| case | term | ours | DeepSeek | rel |
|---|---|---|---|---|
| `saturated_conf` | conf | 8.121124268 | 20.2572594 | 5.99e-1 |
| `no_confidence_head` | conf | 6.931470633e-1 | 0.000000000 | 6.93e-1 |
| `saturated_conf` | total | 9.308561325 | 21.4446983 | 5.66e-1 |
| `no_confidence_head` | total | 2.062782764 | 1.369635463 | 3.36e-1 |

Two independent causes, both in `src/lib.rs:202-213`:

1. **Wrong numerical space for the confidence term.** Upstream uses
   `binary_cross_entropy_with_logits` (`loss.py:151-156`) — the *stable,
   logit-space* form, finite at a confidence logit of ±40. We exponentiate a
   sigmoid **first** and clamp the probability into `[1e-7, 1-1e-7]`, which
   cannot represent that regime: it is capped at `-log(1-1e-7) = 16.1` per
   element, and returns 8.12 where upstream returns 20.26. This is a **SILENT**
   degradation in the ADR-0019 sense — it returns a plausible number, not an
   error.
2. **`Optional` is not expressible.** Upstream's `confidence_pred` is
   `Optional`; a missing head **skips the term entirely** (`loss.py:140`,
   `has_confidence` false ⇒ no confidence term, exactly 0). Our signature takes
   a mandatory `Tensor`, so "no head" can only be spelled as zeros, which the
   code then scores as a *maximally uncertain* predictor at p = 0.5 and charges
   ≈0.693 for.

The fix is one line each. **I did not make it**: this is a numerical change to a
shipped objective, which this project records as a report rather than an edit
(`.bulba/goal.md`: "Числовая правка — отчёт, не редактирование"). It is the
owner's call.

Also worth knowing, because it will bite the next person who tries this: the
upstream `block_keep_mask` must be **`Bool`**, not float. `loss.py:137`
evaluates `block_keep_mask & valid_pred_tokens`, and `&` on f32 raises
`NotImplementedError: "bitwise_and_cpu" not implemented for 'Float'`. A float
mask is a hard crash, not a slower path. `eval_mask` is float (it is
multiplied by the decay weights).

### 2.3 What could a reference have caught that the tests could not?

The window shift of `0e38476` — the one that invalidated every DSpark number
this project ever recorded — is a *data-flow* bug: the window was built from
`targets`, the label sequence, so the head was fed the byte it had just
predicted. `dspark_aux_does_not_read_the_label_sequence` catches it, and it is a
good test. But it catches it by asserting a *property of our own wiring*
("the label sequence must not move this number"). A property test cannot tell
you the number is the wrong number; only a reference can. Nothing in the tree
ever computed the DSpark loss the way DeepSeek computes it, so the two
confidence-term defects above had no gate at all — and they are in the term
that was **on by default at weight 1.0**.

### 1.4 The test, and the demonstration that it can fail

- generator `tests/oracle/gen_dspark_loss_oracle.py`
- fixture `tests/fixtures/dspark_loss_oracle.txt` (8 cases, 9 sig digits)
- pinned upstream `tests/oracle/upstream/deepspec_{loss,common}.py`
- test `tests/dspark_loss_oracle.rs`, 8 tests: **6 green, 2 red on purpose**

**It can fail, in two senses, both demonstrated:**

1. It is *failing right now*, on real code, with the two causes named. A red
   test that a maintainer can read and act on is the deliverable; the
   `burn-gdn2/tests/fused_adjoint_f64.rs` precedent is the same shape.
2. The generator **refuses to write a fixture its own gate would call vacuous**:
   it recomputes the per-term numerators and aborts if they miss the official
   scalar by more than 1e-4 relative. That guard fired during development (it is
   why `out_ce`/`out_l1`/`out_conf` can be trusted as an attribution rather
   than a second opinion).

The comparison is collected, not asserted per-term, on purpose: a gate that
stops at the first failure reported *one* defect when there were two.

## 2. burn-bitnet / the e2m1 path — YES it runs, and the grid is right but the tie rule is not

### 2.1 Does a runnable reference exist?

**YES** — and the finding starts with a correction to the task's own premise.

> **`burn-bitnet` contains no e2m1 at all.** The e2m1 grid, `ActFormat::Fp4`
> and `fp4_round` live in **`crates/dormouse-core/src/act_quant.rs`** (plan
> task C6 intends to move them into `burn-bitnet`; that move has not happened).
> The reference is pinned under `burn-bitnet/tests/oracle/` because that is the
> tap, and the comparison test is in **`crates/dormouse-core/tests/e2m1_oracle.rs`**
> because that is where the code is.

- **repo** `https://github.com/pytorch/ao` (torchao)
- **commit** `3972ed015091f659418dedf12edb980a8ca56b53` (2026-09-25)
- **file 1** `torchao/prototype/mx_formats/fp_format_spec.py` →
  `float4_e2m1_interesting_values`, the OCP MX FP4 grid as (value, formula,
  sign, exp, mantissa) rows. The file cites
  <https://www.opencompute.org/documents/ocp-microscaling-formats-mx-v1-0-spec-final-pdf>
  §5.3.2 by URL.
- **file 2** `torchao/prototype/mx_formats/mx_tensor.py::to_mx` — torchao's
  **real block quantizer**, which emits packed 4-bit codes for
  `torch.float4_e2m1fn_x2`. This is what decides the *tie rule*.
- **fetched and run** 2026-09-30, CPU, `torch==2.14.0+cpu`.

Why torchao and not a bare torch cast: `tensor.to(torch.float4_e2m1fn_x2)`
raises `NotImplementedError: "copy_kernel" not implemented for
'Float4_e2m1fn_x2'` — the dtype exists, the CPU cast kernel does not. torchao's
`to_mx` is the CPU-capable reference quantizer for the same format.

### 2.2 Did I run it? What does it agree with us on?

**The grid is CORRECT.** torchao's own table gives eight magnitudes,
`0 0.5 1 1.5 2 3 4 6`, with **0.75 absent** and **0.5 the single subnormal**.
Our `E2M1` is byte-equal to it. So the `9b343d3` fix stands, and
`ActFormat::Fp4.max_value() == 6.0` — the other half of that fix, scaling a
block's max onto the *format's* max rather than onto 1 — is also confirmed.

**The tie rule is wrong.** The grid's seven interior tie points are
0.25, 0.75, 1.25, 1.75, 2.5, 3.5, 5.0. At **every** one, torchao selects the
level with the **even code**: round-half-to-even, the IEEE default and what the
format's hardware does. Our `fp4_round` (`act_quant.rs:137-140`) is an ascending
ladder of `mask_fill(a >= lo)`, which sends every tie **up** the grid.

Measured, in two independent implementations that agree:

| tie | torchao (reference) | round-half-to-even | ours (`ties-up`) | agree? |
|---|---|---|---|---|
| 0.25 | 0.0 | 0.0 | 0.5 | **NO** |
| 0.75 | 1.0 | 1.0 | 1.0 | yes |
| 1.25 | 1.0 | 1.0 | 1.5 | **NO** |
| 1.75 | 2.0 | 2.0 | 2.0 | yes |
| 2.5 | 2.0 | 2.0 | 3.0 | **NO** |
| 3.5 | 4.0 | 4.0 | 4.0 | yes |
| 5.0 | 4.0 | 4.0 | 6.0 | **NO** |

**4 of 7 disagree.** At 5.0 that is 4.0 against 6.0 — a 50 % error, and it is at
the *top* of the range, which is where the block scale puts the most-used values.
Not fixed here: a numerical change to a shipped objective is the owner's call.

### 2.3 The question I was told to ask, answered directly

> *"the grid is 0, .5, 1, 1.5, 2, 3, 4, 6 and anything that emits 0.75 is wrong"*

**Confirmed against a shipping implementation: the grid is those eight numbers
and 0.75 is not among them.** The e2m1 path does not emit 0.75. That specific
defect is dead and stays dead.

The 0.75 question was, however, asking about the **wrong thing**, and that is
the transferable finding: a grid is a *set*, and a set cannot be wrong in a way
that a rounding *rule* can. The rule was never checked, and it is wrong.

### 2.4 What could a reference have caught that the tests could not?

The three existing tests in `act_quant.rs` are all **self-consistency**:
`every_e2m1_magnitude_round_trips` checks each grid level maps to itself, and
`fp4_output_is_always_the_nearest_e2m1_level` checks every output is the nearest
level *by our own search*. A tie **is** nearest to both candidates, so a
ties-up rule and a ties-even rule are *indistinguishable to both tests*. The bug
lives in the question neither asks — **which** nearest level — and the only way
to ask it is a reference that has already decided.

This is the smallest, cleanest argument in the document for tier (a) over tier
(d): a self-comparison cannot see a choice between two equally-valid answers,
because from inside it there is no difference between them.

### 2.5 The test, and a harness bug worth recording

`crates/dormouse-core/tests/e2m1_oracle.rs`, 4 tests: **3 green, 1 red on
purpose**. Fixture `vendor/burn-fused/crates/burn-bitnet/tests/fixtures/e2m1_oracle.txt`.

**The first draft of this test was wrong and said all seven ties failed.** It fed
each tie as its own 1×1 block, and `quant_act` derives its scale from the block
max, so a block whose only element is the tie has `scale = tie/6` and normalises
the value to exactly 6.0 — the top of the grid, every time. It reported "ours
6.000" seven times and looked like a seven-fold defect. The fix is to put all
seven ties plus the format's max in one row, which fixes the scale at 1.0 and
lets the tie points land where they are actually ties. The test now asserts the
anchor element survives as 6.0, so a silently moved scale fails loudly instead
of re-reporting saturation.

That is recorded in the test's own comments, because it is the same class of
error as the `burn-gdn2` incident in AGENTS.md §3.2 — a reference generator that
is wrong *the same way* the kernel is wrong produces a green test on a real bug.
Here the harness was wrong and the test caught it by disagreeing with an
independent Python measurement of the same rule.

- **this is the paper's own authors**: the README's author list is KAIST AI,
  Mila, Google Cloud, Google DeepMind, Google Research, Université de Montréal —
  matching arXiv:2507.10524 exactly.

**Why it does not run here** (measured 2026-09-30, not inferred):

```
ImportError: cannot import name '_static_cache_update' from 'transformers.cache_utils'
```

The module is coupled to a specific `transformers` build. The installed
`transformers` is 5.17.0 and does not export that symbol. So it is **pinned**,
not run — and the file carries a header saying so, because a pinned file that
looks runnable is how a tier gets promoted by accident.

### 3.2 Three divergences, found by READING it

Since it cannot run, these are **reading, not measurement**, and are labelled as
such. Each is a `file:line` claim a maintainer can check in two minutes.

1. **The auxiliary loss is a different loss.**
   `token_choice_router.py:300-306`: upstream's token-choice balancer is
   `P_i = sum(router_probs)/(bs·seq_len)`, `f_i = num_recursion · balancing_ratio`,
   `balancing_loss = sum(P_i · f_i)` — the Switch-Transformer form, over
   *recursion depths*. Ours (`burn-mor/src/loss.rs:32-46`) is
   `mean((sigmoid(s_active) − n/T)²)` over *active tokens* — a squared deviation
   from a uniform budget, per token. These are not the same function; ours is
   not a transcription of anything upstream ships. Our own doc comment already
   says the paper pairs the balancer with token-choice and this crate
   implements expert-choice, so this is a *documented* choice, but the formula
   has no upstream counterpart at all.

2. **Top-k truncates upstream and rounds here.**
   `expert_choice_router.py`: `top_k = max(1, int(capacity_factor * seq_len))`.
   `int()` truncates. `burn-mor/src/routing.rs:93,137`:
   `((t as f32) * keep_frac).round()`. At `keep_frac = 0.5` and `t = 7` these
   give 3 and 4 respectively. A one-token difference in the active set per
   recursion step, at every step.

3. **Upstream sorts the selected indices; we do not.**
   `expert_choice_router.py`, STEP 1: after `torch.topk(..., sorted=False)` it
   does `selected_tokens, index = torch.sort(selected_tokens, dim=1)` with the
   comment *"IMPORTANT: need to sort indices to keep causal order for those
   tokens that are processed in a block"*, and re-gathers the weights
   accordingly. Ours returns `active_idx` in **descending score order**
   (`routing.rs:76-117`, documented as such). For a gather/scatter pair that
   only permutes, so our own round-trip is fine — but any consumer that relies
   on the block seeing tokens in causal order, which is what the comment is
   about, is reading a different order than upstream's.

Also recorded, because it bears on the A/B question and is not ours to decide:
the paper's own authors report MoR **underperforming** at 135M, **+0.8 few-shot**
at 360M, and **losing** at 1.7B against vanilla while having seen 26B tokens
against vanilla's 20B, writing that the design "might not be suitable for
scaling". `use_mor` is off by default in every config. That is the owner's call
and this document does not touch it.

### 3.3 What could a reference have caught?

`load_balancing_loss` has **no test at all** in the crate — `burn-mor` has no
`tests/` directory. So of the three items above, the one that is a pure function
of tensors (the auxiliary loss) is the one with the weakest evidence in the whole
library, and it is exactly the one upstream implements differently. That is the
gap a runnable MoR fixture should close, and it is a *small* extraction: the
balancer is ~6 lines of upstream code with no model dependency, unlike the
router class that needs `transformers`.

**Cheapest path to a runnable reference:** copy the six lines of
`token_choice_router.py:300-306` into a fixture generator (they are pure tensor
arithmetic on `router_probs` and `top_expert_indices`, no model, no cache, no
`transformers`), and compare against `load_balancing_loss` with the same
collect-don't-abort discipline as §1. The router's *top-k* semantics
(divergences 2 and 3) can be pinned the same way, since `torch.topk` +
`torch.sort` are plain torch. **Nothing about the full block needs
`transformers` at all** — the coupling is incidental to this crate's file layout,
not intrinsic to the mechanism. That is the single most actionable sentence in
this document.

### 4.2 One divergence, found in the authors' pseudocode

The README's `block_attn_res` computes

```python
logits = torch.einsum('d, n b t d -> n b t', proj.weight.squeeze(), K)   # K = norm(V)
h = torch.einsum('n b t, n b t d -> b t d', logits.softmax(0), V)
```

— a dot product with **no temperature**. The paper agrees: Eq. (2) is
`α_{i→l} = φ(q_l,k_i)/Σ_j φ(q_l,k_j)` with `φ(q,k) = exp(qᵀ RMSNorm(k))` and
"normalization" (p. 4, and the appendix table at `attnres.txt:967`). **No
`1/√d` anywhere.**

`burn-attnres/src/lib.rs:109,155,180` multiplies its scores by
`scale = d^{-0.5}`. That is standard attention scaling, inherited from softmax
attention over a *sequence*, where it keeps logits O(1) as d grows. Here the
"sequence" is **depth** and the query is a single learned vector `w_l ∈ R^d`
that the paper **initialises to zero** specifically so that α is uniform at
init. The two choices are not equivalent: `d^{-0.5}` changes the effective
temperature of the depth softmax by a factor of `√d`, so the same learned
`‖w_l‖` produces a sharper distribution than the authors' formulation intends.
At `d = 512` that is a 22.6× difference in logit scale.

This is a reading, not a measurement — I did not run the authors' pseudocode —
and the fix is the owner's. It is reported because it is the kind of thing that
is invisible to every possible self-consistency test: a uniformly-scaled
softmax is still a valid softmax.

### 4.3 What this means for the crate

`burn-attnres` is not in the dormouse build (its README says so, and the only
incoming edges are the library facade and a bench probe). Nine bugs, no
upstream, no way to ever obtain a tier-(a) row, and a documented divergence in
the one piece of external material that exists. **The evidence for the deletion
question is now complete; the decision is the owner's, and I have not touched
the crate.** Per the standing rule, nothing was deleted.

### 5.3 What the honest ceiling is

Tier (b) — a transcription of arXiv:2212.07525 and arXiv:2102.06810, labelled as
one. The existing `koleo_loss` is already an *honest* tier (b): its doc comment
says the soft-min with τ=0.25 is a **surrogate for the row-min**, forced by
burn-cuda 0.21's ArgMin reduce crashing under autodiff, and that τ→0 recovers
DINOv2 KoLeo exactly. That is the correct way to write down a deviation. The
cheapest improvement available is not a reference but a **property test**: the
KoLeo loss has a known optimum (embeddings spread uniformly on the sphere), and
"does the loss reach its minimum on a uniform-sphere embedding?" is checkable
with no upstream at all.

## 6. burn-sct — NO reference exists, and none is expected

**Ours by construction.** `burn-sct` implements a truncated-SVD + Stiefel QR
retraction, and the arXiv id its README cites (`2604.00733`, "Spectral Compact
Training") resolves — I checked all ten arXiv ids cited across these six READMEs
against the arXiv API, and all ten are real papers. But a paper is not code, and
there is no upstream repository for this mechanism that I could find.

So tier (b) is the honest ceiling and there is no path to (a) without someone
releasing an implementation. Two things make this cheap to leave alone:

- the crate is **not in the dormouse build** — its README says so, and
  `dormouse-core` builds its TSCT linears from `burn_spectral::SpectralLinear`
  instead, so this crate is the *non-ternary original* and is duplicated by the
  live one;
- its only registered test, `tests/cuda_retract.rs`, is tier (d), and the seven
  `examples/` files are tier (x) (benchmarks and probes) — the classification
  another lane got right on 2026-09-30.

The one thing worth passing to whoever owns `burn-spectral`: a **Stiefel QR
retraction has a textbook property that needs no upstream to test** — after
`retract()`, `UᵀU = I` to f32 precision, and the retraction must be
*idempotent* (retracting twice changes nothing). The second is the one a
self-comparison misses: a retraction that is merely "not obviously wrong" the
first time can still be moving the factors on the second call, which costs the
~53 ms/step the AGENTS.md §3.1 row attributes to retraction and buys nothing.

## 7. The transferable lesson, and the one thing I got wrong

**A self-comparison cannot see a choice between two equally-valid answers.**
Both defects found here are exactly that shape:

- the e2m1 tie rule — a tie is *nearest* to both candidates, so both existing
  tests pass under either rule, and the bug is only visible against something
  that has already chosen;
- the DSpark confidence term — a plausible number, in the wrong numerical
  space, on by default at weight 1.0.

Neither is a "did someone typo" bug. Both are decisions, and decisions are the
one thing a self-comparison structurally cannot check. That is the argument for
tier (a), and it is worth more than the two bugs.

**The thing I got wrong, recorded because the lane is about not doing this:**
my first transcription of the e2m1 rounding rule used a strict `<` where the
Rust uses `>=`, and it reported **6 false mismatches** against torchao. My
first e2m1 test harness saturated its own block and reported **7 false
mismatches**. Both were caught only by reading the Rust and by an independent
second measurement — the same failure mode as the `burn-gdn2` incident in
AGENTS.md §3.2, where the reference generator replicate-padded a short conv the
same wrong way the kernel did and the differential test was green on a real bug
for months. A transcription is tier (b) no matter how confident it feels, and
this session produced two demonstrations of why.
