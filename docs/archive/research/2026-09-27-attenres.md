# AttenRes in dormouse: what it is, whether the crate runs here, and whether it fits

Date: 2026-09-27. Agent: research subagent (no GPU used — see §2).
Scope: `vendor/dormouse-fused/crates/burn-attnres` (2060 lines) vs the published
mechanism vs our loop. Nothing in the repo was modified; nothing was committed.

## 1. What the crate actually does

### 1.1 The mechanism, precisely

`AttnRes` is a single learned vector and a softmax over the depth axis
(`lib.rs:29-31`):

```rust
pub struct AttnRes { pub query: Param<Tensor<1>> }   // one d-vector, ZERO-init (lib.rs:38)
```

`depth_attend(history: &[Tensor<3>], query: Tensor<1>) -> Tensor<3>`
(`lib.rs:98-139`), for `history = [h_0 … h_{L-1}]` each `[B,T,D]`:

| step | code | shape |
|---|---|---|
| `n == 1` → identity | `lib.rs:100-102` | `[B,T,D]` |
| stack history | `lib.rs:121-125` | `[L,B,T,D]` |
| RMS-norm each source | `h/√(Σh²+1e-5)` over D, `lib.rs:128-130` | `[L,B,T,D]` |
| score = dot(query, normed) | `lib.rs:132-133` | `[L,B,T]` |
| **softmax over dim 0 = depth** | `lib.rs:134` | `[L,B,T]` |
| weighted sum over depth | `lib.rs:135-138` | `[B,T,D]` |

Two fidelity notes against the paper:

- **The query is a single d-vector per module, and the key IS the value** (the
  layer output). There is no key projection. That matches paper Eq 3
  (`k_i = v_i = f_i(h_i)`), and it is why the added parameter count is `d` per
  layer, not `d²`.
- **The crate multiplies scores by `d^{-0.5}`** (`lib.rs:104, 133, 158, 388`;
  `fused_attnres.rs:679, 746, 516`). The paper's Eq 2 is `φ(q,k) = exp(qᵀ·RMSNorm(k))`
  — **no `1/√d`**. With a learned query this is absorbable into the query norm, so
  it is an effective learning-rate/temperature change on `w_l`, not a different
  function. Harmless, but it is a deviation and it means our `w_l` is not
  numerically the paper's `w_l`.

### 1.2 Dispatch: three paths, two of which fail *silently*

`depth_attend` (`lib.rs:106-139`) tries, in order:

1. `#[cfg(all(cuda, autodiff))]` → `depth_attend_autodiff::<CudaBare, 64>`
   (`fused_attnres.rs:1213`). Engages only if `l + 1 <= 64`
   (`fused_attnres.rs:1221-1223`). Fused forward (`:1239-1247`) + a custom fused
   backward registered as an autodiff op (`:1102-1155`).
2. `#[cfg(cuda)]` → `depth_attend_cuda` (`fused_attnres.rs:655`). Requires a
   **bare** `CubeTensor` — `cube_of` downcasts `try_into_primitive::<CubeBackend>()`
   to `CubeTensor` (`fused_attnres.rs:84-89`), which fails under `Autodiff`.
3. Tensor fallback (`lib.rs:121-138`), dtype-generic, ~13 kernels.

**Silent-fallback triggers** (all return `None` → path 3, no log, no env var):
`cube_of` downcast failure (any non-bare backend, i.e. ndarray/cpu, or autodiff
without the `autodiff` feature), `d == 0`, or `l + 1 > 64`.

This **violates ADR-0011** ("no silent skips… shape mismatches stop the run; they
are never skipped"). Consequence for us: a fused-kernel failure on sm_120 would
produce a *correct but ~15× slower* step with zero signal in the log. Needs a
`DM_ATTNRES_DEBUG`-style print, or an assert when the fused path was expected
and declined.

### 1.3 Block mode — and why it is **irrelevant to us**

`BlockAttnRes` (`lib.rs:54-90`) + streaming `BlockAttnState` (`lib.rs:168-231`)
+ `step` (`lib.rs:248-282`): intra-block plain sum, inter-block online softmax
via `source_score` + `merge` (2 fused launches per layer output instead of ~15
tensor launches). `two_phase_attend` (`lib.rs:384-463`) implements paper
Algorithm 1, but on `[S,d] × [N,d]` — a **per-vector, decode-time** API, not
batched `[B,T,D]`. Not usable for training.

Block AttnRes exists to cut residual memory/comm from `O(Ld)` to `O(Nd)` under
pipeline parallelism at L=54 (main result: S=6, 9 blocks + embedding = 10
sources). **At our depth — `max_iter=4`, so at most 5 sources — there is nothing
to cut, and the paper's own `N ≈ 8` would exceed L.** Only Full AttnRes is a
meaningful variant for us. The streaming/online-softmax machinery in the crate
is, for us, dead weight.

### 1.4 The fused kernels

Six `#[cube(launch_unchecked)]` (`fused_attnres.rs:104, 175, 275, 301, 544, 607`).
Launches per call site at our depth (L≤5):

- forward: L `attnres_scores_kernel` + `ceil(L/8)` `attnres_chunk_kernel`
- backward: L `stack_copy_kernel` + 1 `depth_attend_backward_kernel` +
  2 `sum_dim` for `d_q` + L 4-D slices for `d_h`

**All eight launch sites are hardcoded `::<f32>`** (`fused_attnres.rs:495, 507,
692, 710, 748, 788`, plus two in the test bench). **`grep -n "dtype\|elem\|DType"`
over the file returns nothing — there is no dtype guard anywhere.**

### 1.5 Two real bugs found by reading (both cheap, both must land before use)

**(a) bf16 silent corruption.** `depth_attend_cuda` obtains the `CubeTensor` via
`cube_of` (which succeeds for a bf16 tensor — it is still a `CubeTensor`) and
then launches `<f32>` kernels over a bf16 buffer. Under `--bf16` our residual
`tensors are bf16 (`loop_block.rs:339`, `h_ctx + y.mul(scale).cast(h_ctx.dtype())`),
so this is **in-band reinterpretation of bf16 bytes as f32, with no fallback** —
the fallback only fires on `None`, and there is no `None` here. `--bf16` is off by
default, so a default run is safe; a `--bf16` run would be silently wrong.
Fix: one `dtype()` check in each of `depth_attend_cuda` / `source_score_cuda` /
`merge_cuda` returning `None` for non-f32 → the tensor path, which is
dtype-generic and correct. **~6 lines.**

**(b) The chunk-cache thrashes on our exact call pattern.** `cached_state`
(`fused_attnres.rs:43-82`) is a `thread_local` **single slot** keyed on
`(g, b, t, d)`, and its own `ponytail:` comment (`fused_attnres.rs:25-29`) says it
exists to avoid ~15 ms of first-touch page faults. But `let g = CHUNK_G.min(l)`
(`fused_attnres.rs:670`) makes `g` take the values 1,2,3,4,5 across our four call
sites → **five distinct keys per step → the cache misses every call and allocates
fresh every time**, i.e. exactly the cost the cache was written to remove. Fix:
`let g = CHUNK_G;` (1 line) — the kernel already bounds reads with
`ga = g.min(l - c*g)` (`fused_attnres.rs:709`), so a padded chunk is safe. Cost: a
permanent `[8,b,t,d]` f32 buffer = 126 MB at `b=10,t=512,d=768`.

```
320235 5650MiB → 323507 5748MiB → 330373 272→5716MiB → 400856 2320→5716MiB → 409456 5748MiB
```

I waited through 18 checks (~13 min of polling) and a further 8-check window; it

### 2.2 Static landmine analysis (CPU work, done in place of the GPU run)

The four landmines named in the brief are **all absent** — and that is by design,
not luck:

| landmine | present? | why |
|---|---|---|
| `Bool → float` cast returns 0.0 | **no** | the only `bool` is `#[comptime] first/last: bool` (`fused_attnres.rs:189-190`), a compile-time constant |
| bf16 matmul broken | **no** | there is **no matmul anywhere** — every dot product is a hand-written shared-memory tree reduction |
| f16 matmul `builtin.fp16` failure | **no** | same |
| top-k → gather OOB / `ILLEGAL_ADDRESS` | **no** | no `top_k`, no `gather`, no `index_select` anywhere in the file |

Writes reductions instead of borrowing burn's matmul, which is exactly the right
call on this stack.

**But one landmine IS present, and it is the documented one.** The fused backward
does **dynamic slicing of a 4D tensor**:

```rust
// fused_attnres.rs:529-537
let dh_full4 = dh_full.reshape([l, b, t, d]);
let dhs = (0..l).map(|li| dh_full4.clone().slice([li..li+1, 0..b, 0..t, 0..d]).reshape([b,t,d]))
```

AGENTS.md: "**Never dynamically slice a 4D autodiff tensor**: cubecl on sm_120
crashes with `CUDA_ERROR_ILLEGAL_ADDRESS`", repeated at `loop_block.rs:176` and
traced to a real incident in ADR-0012. Here the tensor is a *bare* `CubeTensor`
(`Tensor::from_primitive::<CudaBare>`, `fused_attnres.rs:526`), not an autodiff
tensor, so it is not literally the documented case — but it is the same op class,
on the same hardware, in the same backward. **This is the single most likely
sm_120 failure in the crate and it must be smoke-tested before any training use.**

Secondary: the backward allocates `stack` **and** `dh_t` at full `[L,B,T,D]`
(`fused_attnres.rs:482-485`) with no chunking, and re-stacks the history that the
forward's `ChunkState.chunk` already holds. Fine at L≤5 (126 MB), wasteful in
principle.

## 3. The fit

### 3.1 Our chain maps 1:1 onto the paper's

```rust
// loop_block.rs:328
let y = attn.reshape([b,t,d]) + engram_a.reshape([b,t,d]) + ffn;   // <-- f_i(h_i)
// loop_block.rs:336-339
let scale = self.residual_scale.val().clone().reshape([1,1,1]);   // ONE shared scalar
h = h_ctx.clone() + y.mul(scale).cast(h_ctx.dtype());
```

- `v_0 = h0` (embedding), `v_{i+1} = y_i` → exactly the paper's source list
  `(h_1, f_1(h_1), …, f_{l-1}(h_{l-1}))` (Eq 1, Eq 3).
- Our accumulation is a **fixed** `h + scale·y` with a single **learned** scalar
  shared across all four iterations. The paper replaces exactly this.

So the seam is clean and the A/B is a single flag. The mapping is *easy*.

### 3.2 …and yet the fit is poor. The arithmetic that decides it.

The paper's Table 4 ablation (16-layer model, baseline 1.766) is a **ladder**, and
it tells us where our ReZero already sits:

| rung | variant | loss |
|---|---|---|
| fixed unit weights | PreNorm baseline | 1.766 |
| fixed scalar | DenseFormer | 1.767 |
| fixed scalar, recent-only | SWA (W=1+8) | 1.764 |
| **learned scalar** | **mHC** | **1.747** |
| **learned scalar** | **AttnRes "w/ input-independent mixing"** | **1.749** |
| **learned scalar** | **AttnRes Block (S=4)** | **1.746** |
| content-dependent softmax | **AttnRes Full** | **1.737** |
| — | AttnRes w/ input-dependent query (d×d/layer) | 1.731 |
| — | AttnRes w/ sigmoid | 1.741 |
| — | AttnRes w/o RMSNorm on keys | 1.743 |
| — | AttnRes multihead (H=16) | 1.752 (**hurts**) |

**Our ReZero is a learned scalar → it sits on the 1.747-1.749 rung. Full AttnRes
is 1.737. The expected gain is ≈ 0.012 nats.**

That number matters because the headline deltas people quote from this paper are
*not* it. The Table 2 scaling-law deltas (0.020-0.032) are measured against a
**plain PreNorm** baseline with **unit** weights, which we do not run. Strip that
off and 0.012 is what is left — **and 0.012 nats is below our 3-seed detection
floor** (docs/protocols/AB-PROTOCOL.md: seed variance exceeded every recipe difference
measured at 151M; a win must beat the spread across the control's own 3 seeds).

Two more numbers from the same table, both of which cut against us:

- **The multihead ablation HURTS** (1.752 vs 1.746). The paper's conclusion: "the
  optimal depth-wise mixture is largely uniform across channels". Our GR read is a
  *per-channel* low-rank elementwise gate. If GR's per-channel read is what earns
  its keep, that is in direct tension with this paper's finding about depth mixing.
  We have never separated those two effects.
- **The input-independent-mixing ablation is the proof of mechanism**: replacing
  the query/key with learnable scalars drops 1.737 → 1.749. So the win is
  specifically *content-dependent* depth routing, not "learned weights" — which is
  the part we have least of, because our depth axis is 4 wide.

### 3.3 Why depth 4 is the problem

- **The paper's premise does not hold at our depth.** Its motivation is PreNorm
  dilution ("hidden-state magnitudes grow as O(L) with depth, progressively
  diluting each layer's contribution") and "a significant fraction of layers can
  be pruned with minimal loss". At L=4 the growth factor is 4, not 54, and with
  **weight-tied iterations there is no distinct early-layer computation to
  retrieve** — iteration 0 and iteration 3 are literally the same function. The
  thing AttnRes restores selective access *to* does not exist for us.
- **The learned pattern is diagonal dominance.** Fig 8: "Each layer attends most
  strongly to its immediate predecessor… Diagonal dominance indicates locality
  remains the primary information pathway." At L=5 with a shared function,
  diagonal dominance **is** our existing residual. AttnRes converges to what we
  already do.
- **Scale gap: 26×.** The smallest validated point is 194M activated params,
  L=12 blocks = 24 sources (`d=896`, 38.7B tokens, ctx 8192). We are 7.5M with
  5 sources. The closest independent replication, RD-AttnRes, bottoms out at
  **120M** (2.0B tokens, 5 seeds) — still 16× us. **Nothing in the lineage has
  been validated at 7.5M or at depth 5.**
- **What the 48B result actually is.** Kimi Linear, 48B total / **3B activated**,
  27 blocks / 54 layers, 1.4T tokens (1T WSD + ~400B midtrain), Muon optimizer,
  8M-token global batch, ctx 4096→32K. **What transfers to 7.5M: nothing
  quantitative.** The transferable part is the *mechanism* and the *ablation
  ladder* in §3.2 — which is what I used above.

### 3.4 Where the mapping is *easier* than the paper's setting (be fair to it)

- **We already own the query bank.** `iter_embed` is a `[max_iter, d]` tensor
  **initialised to zeros** (`loop_block.rs:113`). A per-iteration AttnRes query is
  structurally the same object. Zero-init is also exactly what the paper
  *requires* (§5: "all pseudo-query vectors must be initialized to zero… prevents
  training volatility"). So the init requirement is already satisfied by
  something we have.
- **No layer specialisation to protect.** The paper needs per-layer queries partly
  to differentiate layers that do different jobs. Weight-tied, all four iterations
  compute the same function, so a per-iteration query is a pure *depth bias* with
  no competing role. In that narrow sense the mapping is cleaner here than in the
  paper.
- **Per-arm queries are the faithful analogue of the paper's pre-attn/pre-MLP
  pair.** The paper applies AttnRes twice per block with *separate* queries
  (`attn_res_proj`, `mlp_res_proj` — Fig 2 pseudocode) and shows pre-attn reads
  broader than pre-MLP (Fig 8). Our 3 arms already have separate
  content-dependent weights (`w_attn/w_mem/w_ffn`, `loop_block.rs:263-265`), so
  the honest per-arm version is 3 queries per iteration. **This is the one
  genuinely promising angle** — it is the paper's own finding that different arms
  want different depth weightings (limitation (1) in §2.1: "different layer types…
  receive the same aggregated state, despite potentially benefiting from different
  weightings").
- **Do not go per-channel.** H=16 hurt. One d-vector per (iteration, arm).

### 3.5 Cost in step time

Shapes: `small` preset, `b=10, t=512, d=768, max_iter=4`, L≤5. Reference step
**1.9 s for 5120 tokens**, of which **~465 ms is fixed cost** and GEMMs are
**2-5%** (`docs/architecture/PLAN.md:229-233`, `docs/research/2026-09-27-scale-ladder.md:16-17`:
"4× tokens at fixed launch count costs only 1.47× time").

| variant | launches | traffic | est. added | % of step |
|---|---|---|---|---|
| Full, 1 query/iter, **fused** | ~76 | ~600 MB | **~1.1 ms** | **~0.06%** |
| Full, 3 queries/iter (per-arm), fused | ~228 | ~1.8 GB | ~3.3 ms | ~0.17% |
| Full, 1 query/iter, **tensor fallback** | ~132 | ~20 GB | ~18 ms | ~1.0% |
| Full, 3 queries/iter, tensor fallback | ~396 | ~60 GB | ~54 ms | ~2.8% |

**The cost is not the blocker, and this inverts the naive expectation.** Our step
is launch-bound, which normally punishes added ops — but the fused kernel
collapses ~33 tensor passes into 6 launches forward and ~33 into 13 backward, and
the whole thing moves ~600 MB, which is ~0.5 ms of bandwidth on this card. The
independent measurement agrees: LR-AttnRes (2607.09694 §4.9, five paired repeats)
measures the **complete training-step** cost of AttnRes at **1.55%/1.54% over FLA
at 1B/4B on H100 and 2.87%/2.97% on B200** — i.e. the mechanism is a rounding
error on a *well-utilised* step, and cheaper still on ours.

Add the cache-thrash fix (§1.5b) and the honest number is **"free if fused, ~1-3%
if it silently fell back"** — and the second half of that is the risk, because you
would not know which one you got.

The only cost that is *not* free is init-scale, see §5.

## 4. The A/B (if it is ever run — see §6 for the priority verdict)

**Flag:** `--set use_attnres=true` — the ADR-0005 single seam
(`schema.rs` default + `override.rs` arm, identical to how `use_gr` is exposed).
Presets keep it `false`.

**Arms** (3 seeds each, `docs/protocols/AB-PROTOCOL.md`):

| # | arm | what it decides |
|---|---|---|
| 0 | control (current recipe, ReZero `scale` init 1.0) | the reference curve |
| 1 | `use_attnres=true` (Full, 1 query/iteration) | does content-dependent depth routing beat a learned scalar at depth 4 |
| 2 | `use_attnres=true` **per-arm** (3 queries/iteration) | the paper's pre-attn/pre-MLP analogue — the only variant with a real mechanism argument behind it |

Arm 2 is the one worth the GPU-hours. Arms 0+1 alone are testing a 0.012-nat
hypothesis (§3.2) that the noise floor will not resolve.

**Metric:** mean held-out **BPB** on the fixed 100 KB window — `ByteStream::rewind()`
before every eval, `--eval-batches 20` (20 × 5 KB), `Module::valid()` (no graph),
3 seeds per arm, same step count (2000-step confirm per ADR-0002).
Anchors on the same window: uniform 8.000, unigram 5.398, 5-gram 2.911.

**Win rule:** arm mean BPB below control mean by **more than the spread across
the control's own 3 seeds**. Anything inside that spread is "no difference" and
the mechanism is **deleted** (ADR-0002: ties delete).

**Kill rules:**

1. BPB not below control mean by > seed spread → **delete**.
2. Any non-finite loss in the confirm run → **kill** (our overfit-NaN is already
   a live risk; AttnRes changes the residual stream's scale, see §5).
3. Step time **+5%** at the same shape with `--timers` on a quiet GPU → **kill**.
   Predicted +0.06% fused / +1% fallback, so this is a sanity check, not a risk.
4. **If the fused path is not provably the one running, the A/B is void** — it
   would be measuring the tensor fallback, not the mechanism. Needs the ADR-0011
   fix first.
5. **`--bf16` is forbidden** until the dtype guard lands (§1.5a).

**Budget:** 3 arms × 3 seeds × 2.7 h = **~24 GPU-hours**, on a card that
docs/protocols/AB-PROTOCOL.md already has **five arms queued ahead of it** (control, pure
CE, dense FFN, working set, rand depth), and which states plainly: *"the GPU is
the bottleneck, not the ideas."*

## 5. The line it sits on: AttnRes vs our ReZero/GR

**They are alternatives at the same seam, not stackable.** AttnRes replaces fixed
residual accumulation with a softmax over *sources*. GR replaces it with 4
*branches* (low-rank elementwise read, per-branch scalar write). You cannot
compose them as drop-ins: combining would mean attending over
4 branches × 4 iterations = 16 sources and projecting the mixture back into the
branch layout — that is a **new mechanism with no evidence behind it**, and the
paper's own H=16 multihead ablation (1.752, *worse* than 1.746) is a direct
warning against multi-branch depth mixtures. Make `use_attnres` and `use_gr`
mutually exclusive at the config seam and assert it loudly (ADR-0011).

**What the evidence actually favours:** *nothing yet, at our scale.*

- ReZero is a learned scalar → per the paper's ladder it is on the 1.747-1.749
  rung. But note the paper **never ran ReZero** — it compared against plain PreNorm
  with unit weights. So "AttnRes beats the baseline by 0.020-0.032" is *not* a
  claim about us.
- GR is multi-stream and learned — structurally much closer to **mHC**, which the
  paper measured at 1.747, i.e. **the same rung as ReZero and below Full AttnRes
  (1.737)**. GR is not obviously the weaker arm.
- **GR has never been A/B'd** (ADR-0017 says so in as many words) and AttnRes has
  never been run here at all. ADR-0017's own framing is the right one: *"We now
  have FOUR implementations of the residual stream and have compared NONE of
  them."*

**The interaction, stated precisely:** our depth axis is a **fixed 4** (ADR-0013,
"Fixed depth by default; PonderNet halting deleted"), all four iterations
weight-tied. AttnRes's entire value is proportional to the number of *distinct*
things a later step can choose to re-read. At L=4 with a shared function, the
paper's own learned solution (diagonal dominance) is the identity of our current
residual. The one lever that could change that is **per-arm** queries, because
our three arms are genuinely different functions reading the same state — which
is precisely the paper's limitation (1).

**One non-obvious interaction to A/B, not assume:** swapping ReZero(`scale`=1.0)
for AttnRes(zero query) changes the residual stream's scale at init from
`h₀ + Σyᵢ` to `(1/(L+1))·(h₀ + Σyᵢ)` — a **factor of 1/5**. Pre-norm makes the
block body scale-invariant, so the arms are unaffected, but the **readout is not
normalised**: `out_proj.forward(h)` (`loop_block.rs:347`) and then `lm_head`. So
this is a real init change with a real effect on the head, not a no-op. Note our
`residual_scale` init is 1.0 *deliberately* (`loop_block.rs:124-130`: init 0
starved the controller gates of gradient). Expect to re-tune; do not assume
neutrality.

## 6. What to adopt INSTEAD, and what contradicts what we shipped

1. **mHC — `burn-mhc`, arXiv 2512.24880 — already implemented, already ours.**
   Same seam, same rung (1.747), multi-stream like our GR and like our controller,
   and it composes with the branch machinery we already have. The paper's own
   comparison puts it 0.010 behind Full AttnRes and 0.021 ahead of PreNorm. It is
   the cheaper comparison of the two, and ADR-0017 already queues it. **Do this
   one first.**
2. **LR-AttnRes — arXiv 2607.09694.** If AttnRes is ever adopted, this is strictly
   the better version: `r = d/4` routing keys with full-width values, measured
   at 1B and 4B to give **lower val loss AND 0.59-1.20% higher training-step
   throughput than standard AttnRes**, with a fused kernel and released code. One
   free trick worth stealing regardless: the routing key is just the **last `r`
   dimensions of the value**, with parameter-free RMS norm. For us
   `r = d/4 = 192` shrinks the score dot from 768 to 192 — irrelevant on a
   launch-bound step, but it is the version to cite, and it is a strictly better
   A/B target.
3. **RD-AttnRes — arXiv 2608.01075.** Independent replication at the closest
   published scale (120M and 343M, 2.0B tokens, FineWeb-Edu, **5 matched seeds,
   10/10 wins**, NLL −0.0301 / −0.0247, ppl −2.97% / −2.43%). Decouples the
   value route from the q/k route for one extra d-vector per layer and no extra
   token-to-token attention. Only relevant if we adopt AttnRes *and* go per-arm.
4. **Contradicts something we shipped:** the multihead ablation (1.752 vs 1.746)
   says the depth mixture should be **uniform across channels**. Our GR read is a
   *per-channel* low-rank elementwise gate. That is tension with this paper's
   finding about depth routing, and we have never separated "GR helps because of
   the per-channel gate" from "GR helps because of the multi-stream split". An
   AttnRes A/B would sharpen that, which is an argument *for* running it — but it
   is also a reason to expect the win to be small.
5. **Zero-init is a real constraint we have already met** (paper §5; our
   `iter_embed` is zero-init at `loop_block.rs:113`). One thing we should *not*
   copy: the paper's own note that w/o RMSNorm on keys degrades both variants
   (1.743 / 1.750) — the crate does implement it (`lib.rs:128-130`), correctly.

## 7. Verdict

**The code works; the mechanism is a poor fit; the priority is last.**

- **Name: RESOLVED.** arXiv **2603.15031** "Attention Residuals", Kimi Team,
  2026-03-16. **VERIFIED** from the primary PDF. Official repo
  `MoonshotAI/Attention-Residuals` (3516★). Lineage: 2607.09694, 2608.01075.
- **Crate: real, CPU-verified, CUDA-unverified on this card.** 8/8 ndarray tests
  pass. `cuda,autodiff` compiles clean. **The fused kernels have never been
  executed on sm_120** — the GPU was held by another agent for the whole session
  and I did not contend. It is also **not wired into dormouse at all** (no dep, no
  reference, one of ADR-0017's 16 invisible crates). Two real bugs found by
  reading: **bf16 reinterpretation with no dtype guard** (silent corruption under
  `--bf16`) and a **single-slot cache that thrashes on our exact 1,2,3,4,5 call
  pattern**, negating the cache's stated purpose. One genuine sm_120 hazard:
  **dynamic 4D slicing in the fused backward** (`fused_attnres.rs:529-537`).
- **Fit: the mapping is easy, the payoff is not there.** ReZero is a learned
  scalar, which the paper's own ladder places at 1.747-1.749; Full AttnRes is
  1.737. **Expected gain ≈ 0.012 nats — below our 3-seed noise floor.** The
  premise (PreNorm dilution, buried early layers, prunable depth) is an L=54
  problem; at L=4 weight-tied the paper's own learned solution (diagonal
  dominance) *is* our existing residual. Nothing in the lineage has been validated
  below 120M; we are 7.5M. **Block mode is irrelevant** (its O(Ld)→O(Nd) motive
  needs L≫N; at L=5, N=1).
- **LOC: ≈22** (≈40 per-arm), including the two mandatory crate fixes.
- **Cost: ~1.1 ms (~0.06%) with the fused path, ~18 ms (~1%) if it silently fell
  back.** Cost is not the objection; the *invisible* fallback is.
- **A/B: `--set use_attnres=true`, 3 seeds/arm, held-out BPB on the fixed 100 KB
  window, kill on "not below control mean by > the control's own seed spread" or
  +5% step time. 3 arms × 3 seeds = ~24 GPU-hours.**
- **Recommendation: implement the two crate fixes, smoke it on the card for the 4D
  slice, and put the A/B behind the five arms already queued — and put mHC
  (already implemented, same seam, same rung) ahead of it.** The crate's doc
  comment numbers (GPQA +7.5, HumanEval +3.1, MMLU +1.1) are **verbatim-correct**
  from the paper's Table 3, but they are single-model 48B downstream deltas; the
  number that would govern an A/B for us is the 0.012-nat validation-loss rung
  difference, and the doc comment does not say so.
