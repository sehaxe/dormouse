# FP8 on SM120: measured, and why it is not the next lever

**Date:** 2026-11-08. **Card:** RTX 5070 Ti, `torch.cuda.get_device_capability() == (12, 0)`,
torch 2.13.0+cu129. Measurements taken while E1 held the card at 100%, so the
absolute milliseconds are inflated; the RATIOS are what this note is about.

The question came from DeepSeek's infra: their one transferable training
contribution is FP8 (V3: 671B trained in FP8, 2.664M H800-hours, no rollbacks).
`DeepGEMM` requires **SM90 or SM100** and this card is **SM120**, so the kernel
library itself cannot run. What can run is `torch._scaled_mm`.

## What the probe found

Shape: the dense stack's real GEMM, `[8192, 832] @ [3072, 832]ᵀ`.

| | measurement |
|---|---|
| `_scaled_mm` accepts the shape | **yes** (e4m3 in, bf16 out) |
| bf16 GEMM | 1.037 ms |
| fp8 GEMM | **0.526 ms (1.97×)** |
| per-tensor quantize of both operands | **0.423 ms** |
| fp8 end to end incl. quantize | 0.949 ms → **1.09×** |
| per-row `scale_a` (the fix for outliers) | **refused**: "Invalid scaling configuration … scales should be per-tensor" |
| accuracy, per-tensor, with one 40× outlier row | max abs err 0.81 on a signal of ~0.58 → **unusable** |

## The three findings, in order of importance

1. **The GEMM win is real: 1.97×.** FP8 tensor cores work on this card.
2. **The quantize eats it.** 0.423 ms of pure elementwise work (amax reduction,
   fp32 divide, cast) against a 0.526 ms GEMM. End to end the lane is 1.09×, not
   2×. A fused quantize kernel would cut that to ~0.1 ms and the lane to ~1.6× —
   that is a kernel to write, not a flag to flip.
3. **Per-tensor scaling is the only mode torch gives us here**, and our
   activations have outliers (LayerNorm outputs always do). DeepSeek's per-128×128
   block scaling is exactly the thing that makes FP8 trainable, and it needs a
   custom kernel — cuBLASLt's `_scaled_mm` has no block-scaled variant on SM120.

## Verdict

**FP8 is a kernel project, not a config rung.** For the step it would buy at most
`136 ms → ~99 ms = 1.37×` (GEMMs are 104 ms of the step), and only after writing:

- a fused e4m3 quantize with per-row scales (~100 lines of Triton), and
- a per-row/per-block scaled GEMM (the part `_scaled_mm` refuses).

That is 1.37× for a kernel project with a live precision risk. The batch sweep is
one line and may give 1.2-1.4× with no precision risk at all. **Deferred.**

## What survived from the DeepSeek look

Not the kernels — the recipe discipline, which is now on the queue through other
work: warmup (absent everywhere here), weight decay 0.1 (the field does not
exist), gradient clip 1.0, and the LR the warmup unlocks. Those are the items
that cost one config line each.
