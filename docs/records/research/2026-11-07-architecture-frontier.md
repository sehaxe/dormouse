# Архитектурный фронтир при 95M–1B: что опубликовано, что применимо, где потолок

**Дата:** 2026-11-07. **Режим:** read-only; ни конфиг, ни код, ни GPU не трогались.
**Вопрос владельца:** «быть умнее DeepSeek V4.1 Flash при равных параметрах… самая умная и самая эффективная архитектура в мире».
**Что здесь есть:** перевод вопроса в измеримые величины, публичная архитектура V4.1-Flash, 15 кандидатов с числами, арифметика потолка и три следующих эксперимента.

**Метки:** **[T]** — число прочитано в таблице/тексте статьи · **[C]** — посчитано мной из чужих или наших чисел (формула показана) · **[S]** — спекуляция, прямого измерения нет · **[ours]** — измерение этого репозитория.

**Коротко о методе.** ~17 запросов к arXiv, 7 полных текстов, 40+ абстрактов. Каждое число ниже — из конкретной таблицы/секции; номер назван. Где число взято из прошлого отчёта репозитория, а не проверено заново, это сказано явно. Где проверить нельзя — написано «не проверено», а не выдумано число.

## TL;DR

1. **DeepSeek-V4.1-Flash — документированная публичная архитектура**, не миф: arXiv:2609.19969v1 (2026-09-17), 552B backbone + 196B Engram, 40 слоёв (20 encoder + 20 decoder), MoE 1 shared + 384 routed, top-6, d=5120, 8B active на prefill / 16B на decode, 1M контекста, 45T токенов [T, abstract + §2.1 + §4.2.1].
2. **Это модель на 552B, а не «V4.1 Flash = 95M-класс».** Разрыв с нашим 95 035 200: **5808× по параметрам**, **2.3e7× по FLOPs обучения**, **1.7e5× по токенам** [C]. Ни одна ось «равных» не даёт осмысленного сравнения — раздел 3.
3. **Ни одна опубликованная архитектура не даёт выигрыша по BPB при 95M и ≤1GB данных.** Все положительные числа — либо ≥1B параметров, либо ≥16B токенов, либо ≥10GB байтов. Это не мнение: в таблице 2 у каждого кандидата стоит масштаб, на котором число получено.
4. **Наш потолок определяется данными, а не архитектурой.** 98.3MB при 95M — это **1.03 байта на параметр**; оптимум по байтовому закону — **≈50 байт/параметр** (≈4.8GB) [C из T, 2610.05978v1 Table 8]. 1GB всё ещё в 4.6× ниже оптимума, 10GB — около, 100GB — уже упор в ёмкость и в скорость карты.
5. **Предсказание BPB для 95M:** 1GB → **1.16–1.42**, 10GB → **0.91–1.18**, 100GB → **0.84–1.10** (диапазон: сырой закон … калибровка по нашим двум точкам) [C]. Сейчас 1.927 при 98.3MB и 1.519 при 268MB [ours].
6. **Сверка нашей кривой с литературой:** закон предсказывает перепад **0.461 BPB** от 98.3MB к 268MB, мы измерили **0.408** — 89% [C]. Постоянный сдвиг **0.265 BPB** описывает обе точки с остатком ±0.026. То есть по наклону мы совпадаем с литературой, по уровню — на 0.26 BPB ниже (другой корпус/окно eval).
7. **«Обыграть V4.1-Flash» — не фальсифицируемая цель при 95M.** Фальсифицируемая цель: BPB при фиксированных параметрах, байтах и времени против плотного контроля. Всё остальное — маркетинг.
8. **Три следующих эксперимента:** (1) данные до 1GB — ожидаемо −0.51…−0.77 BPB, 4.6 GPU-ч; (2) ByteFlow при 95M — −0.10…−0.30 BPB, ~2 GPU-ч; (3) дистилляция из 3× байтового учителя — −0.03…−0.08 BPB, ~21 GPU-ч. RLVR отклонён: при 134.5M в одном прогоне GSM8K **1.82% → 1.59%** (хуже) [T, 2606.22189v1 abstract; автор сам пишет, что это failure mode, а не нижняя граница].

## 1. DeepSeek-V4.1-Flash: что реально опубликовано

### 1.1 (a) Опубликованная архитектура

Источник: **arXiv:2609.19969v1**, «DeepSeek-V4.1-Flash: Pushing the Limits of KV Cache Compression», DeepSeek-AI, v1 2026-09-17.

| Параметр | Значение | Где именно |
|---|---|---|
| Backbone-параметры | **552B** | abstract |
| Engram-параметры | **196B** (итого ~748B) | §2.1 Overview |
| Активные параметры | **8B prefill / 16B decode** | abstract, §2.1 |
| Слои | **40** = 20 causal encoder + 20 decoder | §2.1 |
| d_model | **5120** | §4.2.1 Model Setups |
| Query heads × head_dim | **64 × 512**, query compression 1280 | §4.2.1 |
| MoE | **1 shared + 384 routed**, top-**6**, expert d_ff **2304**, SwiGLU clamp 10 | §4.2.1 |
| Attention | pure **CSA2** (не CSA+HCA, как V4); encoder m=2, decoder m=1; top-k 512; indexer 32×128; SWA window 128 | §4.2.1 |
| KV cache | **890 байт/токен** глобального KV; ~1/4 от V4-Flash; persistent ~1/8 | abstract |
| Контекст | **1M токенов** | abstract |
| Обучение | **45T токенов**, мультимодальный корпус | abstract |
| Токенизатор (vocab) | **не указан** в прочитанных секциях | не проверено |
| Оптимизатор | Muon + Sinkhorn-балансировка; FP4 main KV | §4.5 |

Что это значит по-человечески: **почти вся архитектурная работа V4.1-Flash — про стоимость инференса на 1M контекста**, а не про качество на параметр. CSA2, CED (encoder-decoder), FP4 KV, SWA Bounded Replay, 890 байт/токен — это про HBM, SSD и prefill, не про BPB при 95M. Из качества-релевантного там: fine-grained MoE, Engram, mHC, Muon. Три из четырёх у нас уже есть или проверены (Muon — да, Engram — да, mHC — да, и mHC/AttnRes у нас дали tie на 9M).

### 1.3 (c) Мои выводы из этого (не факты статьи)

- **[S]** V4.1-Flash — это в первую очередь **инференс-оптимизация**: 552B при 16B active и 890 B/token KV. Владелец сравнивает себя с моделью, чей главный инженерный выигрыш лежит в другой плоскости.
- **[S]** Из архитектуры V4.1-Flash при 95M и 1K контекста переносимы только три вещи: fine-grained MoE, Engram, mHC. MoE требует данных (см. 2.2), Engram у нас уже дал tie на 9M, mHC/AttnRes — tie. CSA2/CED/FP4 KV при 1K контексте не дают ничего: KV-кэш на 1K — это единицы мегабайт.
- **[S]** Заявленные бенчмарки нельзя перевести в BPB и обратно. Между «BPB 1.0 на нашем корпусе» и «MMLU-Pro 74.1» нет опубликованного отображения; любое утверждение «наши 95M умнее» без общего харнесса — не проверяемо.

### 2.2 Что таблица говорит на самом деле

**Все положительные результаты лежат выше нашего масштаба.** Ближайшие:
- MoE-закон: минимальный прогон **16B токенов** (у нас 0.098–1GB = 0.1–1B байтов).
- GDN: **1.3B / 100B токенов**.
- xHC: **18B**.
- Дистилляция байтов: **1B / до 1T байтов**.
- MoD: **60M**, но выигрыш — в шагах, не в BPB при равном времени.

**Единственные проверенные здесь числа ≤1B:** MoD (60M–1B, но это не BPB-выигрыш), MoR 135M (**хуже**), L20-Edu-135M (data recipe, 13B токенов). Ни одного «архитектура X даёт −0.1 BPB при 95M и 1GB».

**Байтовый закон (2610.05978, Table 8) — самый важный источник для нас**, потому что он (a) байтовый, (b) с плотным контролем, (c) с опубликованными коэффициентами. Проверка на наших данных:

- Закон: `L(M,V) = E + A·M^-α + B·V^-β`, M = FLOPs/токен, V = байты.
- Наш M = 6N + attention = 6×95 035 200 + 12 слоёв × 12 × 13 × 64 × 1024 = **692.9M FLOPs/байт** [C].
- При V=98.3MB закон даёт **2.218**, при 268MB — **1.758**; перепад **0.461**.
- Наши измерения: **1.927** и **1.519**; перепад **0.408** = 89% от предсказанного [C].
- Постоянный сдвиг 0.265 (наш уровень ниже) описывает обе точки с остатком **−0.026 / +0.026 BPB** [C].

Это значит: **по наклону мы не хуже литературы; мы просто на более лёгком корпусе/окне**. И это же значит, что экстраполяция закона с калибровкой — не фантазия, а единственная честная оценка. Слабое место: сдвиг 0.265 — это разница **уровня**, и я не знаю, корпус это, eval-окно или readout; поэтому прогнозы ниже даются диапазоном.

### 2.3 Ранжирование (delta × применимость / усилие)

Формула: `score = |Δ BPB| × applicability / GPU-часы`. Applicability: 1.0 — можно запустить сегодня на 95M/≤1GB; 0.1 — нужны ≥100B токенов или ≥10B параметров.

| Ранг | Кандидат | Δ BPB (лучшее число) | Appl. | Часы | Score | Почему здесь |
|---|---|---:|---:|---:|---:|---|
| 1 | **Данные 98MB → 1GB** | **0.51–0.77** [C] | 1.0 | 4.6 | **0.11–0.17** | Единственный рычаг с измеренным наклоном на нашем масштабе |
| 2 | **ByteFlow при 95M** | **0.10–0.30** [S, ours 9M: −0.481] | 1.0 | ~2 | **0.05–0.15** | Наш собственный pre-registered выигрыш; атакует bytes/sec, а не FLOPs |
| 3 | **Дистилляция из 3× учителя** | 0.03–0.08 [S] | 1.0 | 21 | 0.0015–0.004 | Лучший пост-тренинг по литературе; дорого |
| 4 | **Модель 95M → 300M** | 0.06–0.08 [C] | 1.0 | ~15 | 0.004–0.005 | Не «равные параметры», но честная альтернатива |
| 5 | **TST + hash** | ~0 при ≤2GB [C] | 0.6 | 4.6 | ~0 | Эффект появляется после ~10GB |
| 6 | **MoD** | 0 BPB при равном времени [T] | 0.3 | 3 | ~0 | Launch-bound тренер: экономия FLOPs не станет экономией времени |
| 7 | **mHC / xHC** | **n/a (+4 балла на 18B)** [T] | 0.05 | 50 | ~0 | Масштаб не тот; у нас mHC уже tie |
| 8 | **MoE fine-grained** | отрицательно при <16B токенов [T] | 0.1 | 6 | <0 | Данных не хватает |
| 9 | **MoR / loop** | **+0.0155 хуже** при 135M [T] | 0.2 | 3 | <0 | Отрицательно на нашем масштабе |
| 10 | **GDN/KDA hybrid** | 0 при 100M [T] | 0.2 | 5 | ~0 | Кроссовер выше |
| 11 | **RLVR** | **−0.23 pp** GSM8K при 135M [T] | 0.5 | 2 | <0 | Измеренно хуже |
| 12 | **muP** | 0 при фиксированном N [T] | 1.0 | 0 | 0 | Инструмент тюнинга, не способности |
| 13 | **Дедуп** | ~0 для малых моделей [T] | 0.8 | 4 | ~0 | Не рычаг |
| 14 | **Engram (наш)** | tie на 9M [ours] | 1.0 | 4.6 | 0 | Уже проверен, не повторять |

**Отклонённые кандидаты и почему** (правило «не первый хит»):
- **MoE** — единственный механизм с чистым iso-quality выигрышем (0.175× FLOPs на 2B), но его минимальный прогон — 16B токенов; наш корпус в 16–160× меньше. При 100M и 1GB закон предсказывает **хуже**, не лучше.
- **MoR/loop** — на 135M **хуже** на 0.0155 при isoFLOPs; наш прошлый отчёт уже показал, что 1 блок × 3 итерации = 14% ёмкости контроля.
- **MoD** — выигрыш в шагах, а не в loss при равном времени; наш тренер launch-bound, поэтому 66% ускорения шага не материализуются в 66% больше байтов.
- **GDN/KDA** — −14.1% ppl на 1.3B, но при 100M в контролируемых таблицах tie; наш KDA уже проиграл плотному на 0.13–0.37 BPB.
- **mHC/AttnRes** — tie на нашем масштабе (repo), xHC — 18B.
- **RLVR** — при 134.5M измеренно ухудшает; и 2504.13837 говорит, что RLVR не добавляет новых паттернов, а дистилляция добавляет.
- **muP** — не архитектура; при фиксированном N и уже тюненном LR дельта 0 по построению.
- **TST+hash** — ниже 10GB фит даёт нейтрально/хуже; это data-scale-dependent эффект.

## 3. Честный потолок: арифметика

### 3.1 Три оси «равенства» и почему все три ломаются

| Ось | V4.1-Flash | Наш 95M | Отношение |
|---|---:|---:|---:|
| Параметры (backbone) | 552e9 | 95.035e6 | **5808×** |
| Активные параметры decode | 16e9 | 95.035e6 | **168×** |
| Токены обучения | 45e12 | 268e6 (байты) | **1.68e5×** |
| FLOPs обучения (6·N_active·D) | 4.32e24 | 1.86e17 (268MB, с attention) | **2.3e7×** |
| FLOPs/токен инференса (2N) | 32e9 | 190e6 | **168×** |

Расчёты: 6×16e9×45e12 = 4.32e24 [C]; наш M=692.9e6 × 268e6 = 1.86e17 [C]. Для MoE это приближение (только активные эксперты), attention и мультимодальность не включены — но порядок верен.

**Вывод:** «равные параметры» невозможны (5808×), «равный compute» невозможен (2.3e7×), «равные FLOPs/токен» невозможны (168×). Сравнение имеет смысл только при **всех трёх одновременно равных** — то есть между двумя 95M моделями на одном корпусе с одним бюджетом. Это и есть наш A/B.

### 3.2 Сколько байтов нужно 95M: оптимум по байтовому закону

Из Table 8 (byte raw) и eq. 15: `V*/N* = (βB/(αA))^{1/β} · M^{α/β} / N`. При наших M=693M, N=95M:
`V*/N* ≈ 209 · 693e6^0.8323 / 95e6 ≈ **50 байт/параметр**` [C].
Это ≈ **4.8GB** для 95M. Для сравнения, Chinchilla — 20 токенов/параметр = 1.9GB в байтовом эквиваленте (1 байт = 1 токен) [T, 2203.15556 Appendix Eq. 10 + Table 3]; байтовый закон даёт в 2.5× больше, потому что байтовая модель тратит больше compute на токен.

| V | Байт/параметр | Статус | Оптимальный N по закону |
|---:|---:|---|---:|
| 98.3MB | **1.03** | в 49× ниже оптимума — data-limited | ~2M (но модель слишком мала) |
| 268MB | **2.82** | в 18× ниже | ~5M |
| 1GB | **10.5** | в 4.8× ниже | ~20M |
| 10GB | **105** | в 2.1× выше — near-optimal | ~200–250M |
| 100GB | **1052** | в 21× выше — capacity-limited | ~2–3B |

«Оптимальный N» — из `V/N ≈ 928·N^-0.1677` [C], порядок, не точное число. При V < 1GB колонка экстраполирует ниже диапазона фита и означает только «модель слишком велика для такого объёма данных», а не «надо тренировать 2M».

### 3.3 Предсказанный BPB для 95M при 1/10/100GB

Формула: `L = E + A·M^-α + B·V^-β`, M=692.9M, коэффициенты byte raw из Table 8. Колонка «калибровка» — тот же закон минус 0.265 (постоянный сдвиг наших двух точек).

| V | Сырой закон [T+C] | Калибровка [C] | Наше измерение |
|---:|---:|---:|---:|
| 98.3MB | 2.218 | 1.953 | **1.927** |
| 268MB | 1.758 | 1.493 | **1.519** |
| 1GB | **1.420** | **1.155** | — |
| 10GB | **1.176** | **0.911** | — |
| 100GB | **1.100** | **0.835** | — |

Читать так: **1GB → 1.16–1.42**, **10GB → 0.91–1.18**, **100GB → 0.84–1.10**. Нижняя граница — если наш корпус так же легче литературы, как в двух измеренных точках; верхняя — если сдвиг исчезнет.

Оговорки, без которых число — ложь:
- **[S]** 1GB ниже диапазона, на котором фитился закон (их свип — до ~1e20 FLOPs, но точный минимум V в Table 8 не напечатан). Экстраполяция вниз на 1–2 порядка.
- **[S]** Калибровка 0.265 — это разница уровня, а не наклона; я применяю её ко всей кривой, включая E. Если корпус просто легче, E тоже должен быть ниже — тогда калиброванные числа честны. Если разница — от нашего eval-окна/readout, калибровка завышает оптимизм.
- **[T]** 95M при 100GB — за пределами ёмкости: A-терм при 95M равен 0.19 BPB и не падает с данными. Модель 1B имела бы A-терм ~0.07.

### 3.4 Где начинается осмысленное сравнение

- **По параметрам:** 95M vs 95M — единственное честное. V4.1-Flash в 95M-версии не существует; его архитектуру нельзя «уменьшить» без смены всего (384 эксперта при 95M total = 0.25M на эксперта, это не MoE, это шум).
- **По compute:** наш бюджет 1.86e17 FLOPs; на таком бюджете V4.1-Flash успевает 0.0007 токена — сравнение бессмысленно.
- **По FLOPs/токен инференса:** 168×. Чтобы сравняться, нужен 8B-active MoE, а это уже не 95M.
- **По качеству:** у V4.1-Flash нет опубликованного BPB (только Figure 6 без чисел), у нас нет бенчмарк-харнесса. Общего языка нет.

**Итог:** «быть умнее V4.1-Flash при равных параметрах» — не измеримая цель. Измеримая: **«при 95M, 1GB, 4.6 GPU-ч получить BPB ≤ 1.42 и не хуже плотного контроля на том же бюджете»**. Вот это можно проверить и опровергнуть.

## 4. Три следующих эксперимента (ранжированы)

Все цены — при 60 kB/s для 95M (ваша цифра), линейно по N для других размеров; evals и checkpointing включены грубо, ±20%.

### Эксперимент 1 — ДАННЫЕ: 98MB → 1GB

- **Изменение конфига:** тот же 95M dense (`block_form="transformer"`, 12 слоёв, d=832, s=1024, b=8×3), тот же оптимизатор Muon+AdamW, тот же LR-график; корпус — 1GB уникальных байтов вместо 98.3MB. Шагов на байт столько же, сколько в 268MB-прогоне (то есть 10.7× шагов, а не 10.7 эпох).
- **Ожидаемая дельта:** **−0.51…−0.77 BPB** от 1.927 → **1.16–1.42**. Основание: Table 8 byte raw, β=0.508, калибровка 0.265 [C]. Это самый большой ожидаемый выигрыш из всех кандидатов.
- **Цена:** 1e9 / 60e3 = 16 667 с = **4.63 GPU-ч** на один проход; с eval ×1.1 ≈ **5.1 ч**.
- **Фальсификатор:** если BPB при 1GB **> 1.60** (выигрыш < 0.33), закон β не переносится на наш корпус → данные перестают быть рычагом, следующий бюджет идёт в ёмкость (300M) или в ByteFlow. Порог ставится до прогона.
- **База:** 2610.05978v1 Table 8 (E, A, α, B, β); наши две точки 1.927/1.519 как калибровка.
- **Почему первым:** единственный механизм, у которого наклон измерен **на нашем масштабе** и **на нашем корпусе**, а не перенесён с 1B.

### Эксперимент 2 — АРХИТЕКТУРА: ByteFlow при 95M

- **Изменение конфига:** `use_byteflow=true`, патч-канал 512B → 128 патчей (4× сжатие), loop/KDA как глобальная стадия, `d_global` масштабировать до ~95M суммарно; контроль — плотный 95M на тех же байтах и том же wall-clock.
- **Ожидаемая дельта:** **−0.10…−0.30 BPB**. Основание: наш pre-registered trio при 9.2M: ByteFlow **3.466** vs plain9m **3.947** = **−0.481 BPB** при равных параметрах и байтах [ours]. Перенос на 95M — экстраполяция: с ростом модели преимущество сжимается (BLT при 1B уже хуже BPE, кроссовер 7B — [T, 2412.09871v1 §5.1]).
- **Цена:** при 4× сжатии последовательности throughput ~4× выше: 268MB / (4×60kB/s) ≈ **0.31 ч** на арм; два арма × 2 сида + eval ≈ **2.0 ч**.
- **Фальсификатор:** если ByteFlow при 95M **не лучше плотного на ≥0.03 BPB** при равных байтах и равном wall-clock — механизм не масштабируется, канал закрывается (не «нужно больше шагов»).
- **База:** 2603.03583v1 (ByteFlow, Table 6 — сжатие vs accuracy); наш 9M A/B (`docs/records/reviews/byteflow-ab-2026-10-02.md`, `benches/history.tsv` 2026-10-03).
- **Почему вторым:** это единственная архитектура с **нашим** положительным измерением, и она бьёт именно в bytes/sec, а не в FLOPs — а тренер launch-bound.

### Эксперимент 3 — ПОСТ-ТРЕНИНГ: дистилляция из 3× байтового учителя

- **Изменение конфига:** сначала учитель 300M (та же байтовая архитектура, тот же корпус 1GB, CE), затем студент 95M обучается на **KD-лоссе по 256-байтовому словарю** (полные логиты, без top-k — байтовый словарь это позволяет) на том же 1GB; сравнение — студент с CE на тех же байтах.
- **Ожидаемая дельта:** **−0.03…−0.08 BPB** у студента против CE-близнеца. Основание: 2609.12303v1 — distilled byte-1B матчит token-1B на **1/6 данных**, +4% асимптотически [T, abstract]; 2502.08606v1 — дистилляция выигрывает у supervised до compute-порога, растущего с размером студента [T, abstract]. Перенос на 95M — [S].
- **Цена:** учитель 300M: throughput ~60×(95/300)=19 kB/s → 1e9/19e3 = **14.6 ч**; студент 95M + teacher-forward ~**6.3 ч**; итого **≈21 ч**.
- **Фальсификатор:** если выигрыш студента **< 0.02 BPB** над CE-близнецом при равных байтах — дистилляция не платит при 95M, пост-тренинг закрывается до появления 1B-базы.
- **База:** 2609.12303v1 (byte distillation, 1B/1T bytes); 2502.08606v1 (distillation scaling laws); 2504.13837v1 (дистилляция добавляет capability, RLVR — нет).
- **Почему пост-тренинг, а не RLVR:** RLVR при 134.5M измеренно **ухудшает** GSM8K 1.82% → 1.59% [T, 2606.22189v1 abstract], а 2504.13837 показывает, что RLVR не выходит за пределы base-модели. Дистилляция — единственный пост-тренинг с положительным числом на нашем масштабе.

**Суммарная цена трёх:** ~28 GPU-ч, то есть ~1.2 суток на карте. Это меньше, чем один прогон 100k шагов, который уже делался (12.7 ч), и покрывает оба исторических рычага — данные и пост-тренинг.
