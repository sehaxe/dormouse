# 2026-11-04 — capability baseline: 0 из 4 на претрейн-модели

Первый в проекте замер **способности**, а не сжатия. Гарнесс `scripts/eval_agent.py`
(коммит `ecc0212`), 20 задач из `build_rl_tasks.py` (12 math, 8 code), чекпоинт
flagship 105M, CPU (карта занята 200M-прогоном).

## Результат

| метрика | значение | что значит |
|---|---|---|
| **format** | **0.0 %** (0 / 12) | модель **ни разу** не выдала вызов инструмента: все 12 ответов — проза (`no_call: 12`) |
| **execution** | n/a (0 принятых) | нечего исполнять |
| **task success** | **0 / 20** (math 0/12, code 0/8) | ни одна задача не решена |
| **escape audit** | 0 попыток | песоочница не получила ни одного запроса; находок нет |

## Почему это ожидаемо и почему это важно

Модель **никогда не видела** маркеров `\x04..\x07` (шаблон вызова инструмента) — претрейн
шёл на обычном тексте, SFT не запускался. То есть 0 — это корректный замер состояния
«plumbing есть, способности нет», а не поломка гарнесса.

Доказательство, что гарнесс видит разницу: на `--model scripted:valid` те же 12 math-задач
дают **format 1.0, execution 1.0** (`9 passed` в `tests/test_eval_agent.py`, гейт a).

## Что это задаёт

```
baseline (претрейн):     format 0%    success 0/20
цель SFT (4000 шагов):   format 60-90%  ← это и есть проверяемый эффект инструктажа
цель RLVR после SFT:     success > 0 на math-полосе
```

Если SFT не поднимет format с 0 до десятков процентов — значит корпус или шаблон не
работают, и это видно за 4 000 шагов вместо «BPB не двигается, не понимаю почему».

## Оговорки

- CPU-прогон 20 задач занял ~25 минут; на GPU после SFT это секунды.
- Выборка — 20 задач (12 math / 8 code), не бенчмарк: числа сравнимы между чекпоинтами
  при одинаковом `--seed`, но не являются абсолютной оценкой модели.
- `execution` = n/a, когда нет принятых вызовов: это корректный null, а не 0.0 — иначе
  «модель не зовёт инструменты» и «инструменты ломаются» слились бы в одно число.
- BFCL-формат (300 задач) подключается тем же `--tasks`, адаптер не написан.

## Заодно исправлено этой ночью

`build_sft_v2.py` пишет пары как `{"prompt", "response"}`, а `sft` читал только
`{"instruction", "response"}` — **все 11 499 строк** попадали в `chat_dropped_dirty`, и
SFT-прогон стартовал бы на пустом корпусе, выглядя как «фильтр всё отбросил». Тест
`test_chat_jsonl_accepts_our_own_prompt_response_pair` держит оба ключа и приоритет `prompt`.
