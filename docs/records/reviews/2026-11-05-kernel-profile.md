# 2026-11-05 — первый профиль ядер: где на самом деле шаг

## Инструмент

`scripts/kernel_profile.py` (коммит в `main`): `torch.profiler` с CUDA+CPU,
атрибуция ядер к регионам модели (`record_function` вокруг embed / epilogue /
kda_proj / kda_recurrent / csa / engram / moe_dispatch / moe_gemm / attnres /
head / optimizer / clip), агрегация по `(ядро, регион)`, JSON + `--diff`.

Прогон: чекпоинт `m400b` (шаг 20 000), b8×s1024, 3 прогрева + 10 замеров.

## Три вывода, каждый меняет приоритет

1. **Оптимизатор — крупнейший регион (23.5%)**, а в конфиге всё ещё
   `muon_state_dtype=fp32`, `ns_dtype=fp32`, `ns_steps=5`, хотя bf16-состояние
   уже мерили как +18% шага.
2. **MoE-математика — 1.3 мс, а диспатч — 31.6 мс, в 24 раза дороже.** Все наши
   споры про batched/bucketed/share_u касались 0.9% шага. Настоящий вопрос —
   маршрутизация: router GEMM, softmax, topk, argsort, bincount, gather, scatter.
3. **mhc_write 23.2 мс (15%)** — fused-ядро записи residual дороже, чем всё
   внимание вместе (kda+ csa = 22 мс).

## Что это отменяет

Все прежние оценки «38% поэлементные, 25% матмулы, 37% запуски» были сняты на
конфиге с `engram_ram=true` и без fused-эпилога. Профиль по регионам — первая
картина, где каждая цифра привязана к ядру и модулю.

Census поэлементных проходов (`scripts/pass_census.py`) дал 4.17 ГБ и 2.2 мс на
итерацию = 1.8% шага: **точечные операции не виноваты**, гипотеза закрыта числом.
