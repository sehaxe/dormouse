## Что нашлось при чтении первоисточника

`fla/ops/common/chunk_delta_h.py` @ `9f38d249` — **это первоисточник формулы
переноса**, а не транскрипция. Строки 246–284, блок `if USE_G:` / `if USE_GK:`
в конце обработки чанка:

```python
if USE_G:                                  # per-head decay
    b_g_last = exp2(g[... last_idx ...])
    b_v = b_v * where(m_t, exp2(b_g_last - b_g), 0)[:, None]
    b_h1 *= b_g_last                       # ← decay ПЕРЕНОСИМОГО СОСТОЯНИЯ
if USE_GK:                                 # per-key-dimension decay
    b_gk_last1 = gk[..., o_k1, :]
    b_h1 *= exp2(b_gk_last1)[None, :]      # ← ВТОРОЙ, НЕЗАВИСИМЫЙ decay
```

**Два независимых затухания подряд.** У нас:

`src/kernel/chunk_cube.rs:541`
```
S[kk][v] = S[kk][v]·g_last[kk] + Σ_r kgd[r][kk]·v_new[r][v]
```
где `kgd[r] = k_r · exp(g_last) / exp(g_r)` (`:117`), `g_last[kk] = exp(g_left)`
(`:120`) — **однофакторное**, по размерности `kk`, без отдельного слагаемого.

Поиск по `vendor/burn-fused/crates/burn-gdn2/src/` на `gk` / `kg_decay` /
`gk_last` / `STATE_V_FIRST`: **нуль совпадений.** Раздельного затухания по
размерностям ключа у нас нет **вовсе**, и флага выбора такого режима тоже нет.

## Что это значит и почему это НЕ «транскрипция неверна»

`USE_GK` — это **опциональная конфигурация FLA**, а не формула, которую мы
переписали неверно. Наш код реализует `USE_G`-эквивалент: одно затухание. Если
v `USE_GK=False`, формула переноса у FLA совпадает с нашей по виду.

**Значит:** расхождение 5.6e-1 на chunk 1 **не объясняется** отсутствием
`USE_GK`, если только эталон не считает в режиме `USE_GK=True`. Это
**проверяемо и не проверено**, и это первое, что должен сделать следующий
агент: посмотреть, при каком `USE_GK` / `USE_G` построена
`tools/gen_reference_f64.py`, и пересчитать в согласованном режиме.

**Второе, что требует проверки:** у FLA decay обоих слагаемых берётся из
`exp2(...)`, то есть **логарифм по основанию 2**. Наш `g_last` — из
натурального `exp`. Если соглашение по основанию не выровнено при переводе
`g` в `gk`, значения будут согласованы на первом чанке (где перенос ещё не
участвует в накоплении) и разойдутся на втором. **Это объясняет наблюдаемую
форму дефекта лучше, чем отсутствие `USE_GK`.** `burn-kda` явно оговаривает
этот вопрос (`autodiff.rs` `exp2`/base-2 cumsum) — не проверено здесь.

## Сужено до конкретной строки (2026-09-30, чтение кода)

Записаны **все** присваивания в `s_sh` в `chunk_cube.rs` (строки 340–700).
Их ровно три:

| строка | что | путь |
|---|---|---|
| 373 | `s_sh = state[...]` — загрузка входа | до цикла `while t`, один раз |
| **590** | `s_sh = s_sh·glast[cb·kd+kk] + (acc_a+acc_b+acc_c+acc_d)` | **основной путь, перенос** |
| 677 | `s_sh = state_in[...]` | другой путь |

И вычисление `v_new`, **которое читает `s_sh`**:
```
434:  vn_a += w0 * s_sh[kk * vtile + v0];        // v_new = u - W·s
```

**Гипотеза, которую надо проверить первой — расхождение нормировки внутри
чанка.** `kgd[r] = k_r·exp(g_last)/exp(g_r)` (`:117`) нормирует вклад `k` к
**концу** чанка (`gexp_l = gexp[c-1]`). Значит и входящее состояние `s_sh`
должно быть нормировано к тому же концу, то есть домножено на `exp(g_last)`
**до** того, как из него считается `v_new`. Но `:590` применяет `glast`
**после** — `v_new` на `:434` читает ещё не затухавшее состояние.

Это объясняет наблюдаемую форму дефекта точно: на **первом** чанке входное
состояние нулевое, `v_new` не зависит от нормировки, и chunk 0 сходится на
4.9e-8. На **втором** чанке состояние ненулевое — и нормировка проявляется
целиком. Не «где-то расходится», а ровно «со второго чанка».

**Проверяемое следствие:** если гипотеза верна, подстановка
`S ← S·glast` в начало обработки чанка (то есть перенос `:590` в ДО
вычисления `v_new`) должна снять красное. Если красное останется — гипотеза
опровергнута, и следующий кандидат: `glast[cb·kd+kk]` индексируется
`cb = bh·nt + t`, и при `nt > 1` либо при переиспользовании буфера `glast`
между вызовами индекс указывает не на тот блок.

**Замечание к `states_out`:** `:722` пишет финальное состояние **без**
общего decay — то есть наружу отдаётся сырое. Это может быть верно (сырое
состояние и подаётся на вход следующего вызова как `state_initial`), а может
и означать двойное затухание на стыке двух вызовов. Отдельно проверить.

## Чего этот документ НЕ утверждает
